# HealthNext 总体开发计划

## 1. 目标与执行原则

建设企业/矿山健康监测平台，同时沉淀可供后续项目复用的工程基础。面向值班、健康、安全、设备及系统管理人员，支持发现风险、查看人员、处置事件、维护设备和分析复盘。

- **开发顺序**：架构与契约整理 → 完成全部前端 mock → 实现后台与 Oracle 联调 → 真实业务验收。前端阶段定义接口，不提前建设数据库或设备链路。
- **设计基准**：从目标用户任务、产品体验和可复用技术底座出发重新设计。旧系统菜单、页面、数据库结构与实现方式不构成约束；已经投入的页面工作量不构成保留理由。
- **产品结构**：七个业务域、25 个主页面（含登录）作为当前范围基线；A0 按新产品任务验证，确需调整时说明理由并同步清单，不为固定数量牺牲任务完整性。
- **技术基础**：Vue 3、TypeScript、Pinia、Element Plus；后端采用 Java 21、Spring Boot、Oracle。目标为模块化单体，产品业务域不机械对应微服务。
- **复用边界**：应用壳、主题、认证、权限、请求和错误处理属于通用基础；健康指标、手表协议、矿区地图与人体属于业务模块。通用基础不得反向依赖健康业务。
- **设计分工**：创新布局先由 Gemini 提供样板，用户确认后由 Grok 完善工程实现；成熟列表和局部修改复用符合新设计系统及架构标准的组件。生图和 Figma 按需使用。

本文件只管理范围、顺序与进度。字段、交互和视觉验收见 [页面计划](./页面设计计划.md)；接口、业务规则、数据库和运行保障见 [工程计划](./工程实现计划.md)。

## 2. 当前状态与下一步

按新产品标准重新规划，25 个主页面均为待设计、待实现、待验收，不从既有页面数量扣减工作量。本状态描述新方案进度，不对磁盘上的代码进行删除或禁用。

当前执行 A0：明确角色任务、信息架构、页面职责、领域边界和质量门槛。随后完成通用前端底座、契约与集中 mock，并通过代表性流程验证，再逐批完成所有页面。真实后台在全部前端 mock 验收后实施。

## 3. 七个业务域与主页面范围

共 **25 个主页面**。N01–N25 为唯一页面清单；标签、筛选、抽屉、弹窗和异常状态不另计页面，但仍需验收。增减或拆分主页面时同步本清单。

- **应用基础，1 页**：N01 登录。
- **今天，1 页**：N02 工作台。
- **现场，1 页**：N03 现场态势（包含地图、实时名单、值班名单、区域及事件视图）。
- **人员，4 页**：N04 人员档案；N05 人员健康详情（含各指标个人趋势）；N06 沉浸人体；N07 入井健康准入。
- **事件，2 页**：N08 事件中心（包含风险来源、SOS 等设备事件及状态筛选）；N09 处置与追溯（包含历史事件、动作时间线和历史预警查询，区分原始异常记录与处置记录）。
- **设备，3 页**：N10 设备台账；N11 设备控制；N12 通信报文。后两页支持设备上下文及授权范围内检索。
- **分析与洞察，4 页**：N13 分析总览（含事件效率、重复异常与覆盖指标）；N14 多维健康分析（按心率、压力、血压、血氧、睡眠及趋势风险切换，保留部门/班组/班次/区域交叉分析）；N15 报告中心；N16 AI 助手。
- **管理后台，9 页**：N17 用户；N18 角色与权限；N19 组织架构（部门/班组）；N20 岗位与工种；N21 区域配置；N22 班次配置；N23 风险与事件规则；N24 通知与集成配置；N25 系统设置与审计（系统参数、操作日志和审计检索为内部标签）。

地图、指挥和实时监控合并为现场的协同视图；个人指标放在健康详情，群体指标放在多维分析。功能整合不删减来源、严重度、责任人、SLA、误报和追溯能力。公共详情遵守统一交互与契约，历史预警与处置记录必须区分。

导航与路由根据页面职责设计，跨页保留人员、设备、事件、区域和查询上下文；已有路由不作为设计限制。

## 4. 实施顺序

### A0：先确定目标产品与架构设计

先从角色与核心任务定义导航、信息层级、页面职责、完整流程、领域模型和接口边界，明确设计系统、可访问性、响应式及性能验收标准。以 N01–N25 检查任务覆盖，并为每个页面定义验收条件。

从目标方案拆解实现任务，选择满足模块边界、交互与质量要求的实现方式。业务规则以经过核实的领域事实和需求为依据。

**通过标准**：目标任务与页面职责清楚，关键流程及模块边界可评审，每项有验收范围与实施任务。当前 25 页是范围基线，详细目标设计尚待完成。

### A1：统一前端基础

稳定布局、主题令牌、深色控件与弹层、查询分页、表单详情、错误空态和键盘交互。从实际重复用法提取组件，避免每页重新实现主题、刷新和请求状态。

**通过标准**：公共层不引用健康业务；五档视口及弹层、焦点、文字、按钮可达通过检查。

### A2：统一接口契约与 mock

定义人员、设备、事件和实时查询的字段、空值、错误、时间、分页和允许动作。页面通过统一查询/操作接口调用 mock 或 HTTP 实现；场景、固定时钟、关联样本与重置入口集中管理。禁止读取初始种子代替当前状态，禁止演示空态重置共享业务数据。

**通过标准**：契约、类型、样本与测试一致；模拟失败、冲突和分页有真实行为，生产环境不静默回退 mock。

### A3：用代表性业务流程验证新架构

按新设计实现人员—设备—事件 mock 流程，验证改名、绑定、解绑、处置、下钻、返回、分页、失败与过期响应隔离。

**通过标准**：跨页数据一致；移除健康业务注册后，通用登录、布局和基础示例仍可运行。通过后再推广到其他视图。

### 完成全部前端 mock

按七域清单小批推进，每批最多 2–3 个相关视图。依据目标流程、依赖关系和设计风险安排各域批次，不按已有页面数量安排优先级。创新布局确认后再工程化，普通列表使用新设计系统的公共组件。新主页面及内部视图都验收后，才进入后台阶段。

### 真实后台与上线

前端全部完成后，按工程计划 E0–E8 执行。先验证一名人员、一台设备的正常上报 → 持续异常 → 事件 → 确认/分派 → 处理 → 满足条件后关闭，再验证容量、地图、分析与扩展能力。Oracle 版本、环境、正式规则和设备样本在对应阶段核实。

工期根据设计范围、任务拆解与实际交付速度估算。

## 5. 验收标准

**前端 mock 完成**：

- 业务操作可执行，人员/设备/事件上下文、摘要下钻和状态一致；失败、权限拒绝、空数据、陈旧数据与缓存有明确行为。
- 使用统一主题；检查 1920×1080、1440×900、1280×800、1024×768、390×844，包括展开弹层和区域内部操作，不只检查页面宽度。
- 图表有单位、时间范围和样本说明；mock、未接入与真实结果明确区分。页面离开后释放定时器和图形资源。
- 类型检查、构建、契约与相关交互测试通过；保存截图、结果及未验收项。仅截图成功或 URL 改变不算交互通过。

**真实业务完成**：在前端验收基础上，真实 API 与 Oracle 对账通过，服务端权限、重启持久化、并发冲突、幂等、审计和相关设备链路有证据。规则、数据时间与设备异常处理遵循工程计划；未执行的外部动作不能显示成功。

**模板可交付**：公共基础可脱离健康模块运行，依赖边界可检查，干净环境可按统一命令安装、启动、测试和构建；后台阶段补齐迁移、可观测性、部署及恢复验证。不以某个 Agent 的完成报告代替验收。

多租户、插件系统、通用流程引擎、微服务和消息队列按明确需要另行决策。完整三维矿井、全量旧数据导入和大型消息系统不属于当前必做范围。
