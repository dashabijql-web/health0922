# HealthNext 工程架构与后台实施计划

本文定义目标架构、业务不变量、接口和真实后台验收；不是已实现接口清单。范围与当前进度见 [总体计划](./产品设计计划.md)，前端交互见 [页面计划](./页面设计计划.md)。

## 1. 阶段边界与首条真实流程

先完成总体计划 A0–A3 和全部前端 mock，再执行 E0–E8。前端阶段先定义模块与契约，通过 mock 验证；Oracle、真实权限、设备通信和持久化留在后台阶段。页面进度按新方案验收记录计算。

HealthNext 是独立重写项目，采用 Vue 3 / TypeScript / Pinia / Element Plus，后台 Java 21 / Spring Boot 模块化单体，数据库 Oracle，访问层 MyBatis，版本迁移 Flyway。架构围绕新项目的领域边界与质量目标建立，不沿用旧系统模块、表结构或耦合关系。必要的设备协议和业务事实重新验证后使用；旧数据导入仅在明确需要时作为独立边界任务，不影响核心设计。

首条真实流程：登记一人 → 绑定一表 → 收到有效心率/血氧 → 持续异常形成事件 → 确认/分派/处理 → 满足关闭条件后关闭。Oracle 保存记录，刷新页面和服务重启后仍可追溯。先验证一台设备，再验证容量和扩展能力。

## 2. 模板基础与模块架构约束

本节是目标架构，当前未全部实现。前端阶段先定义契约及模块边界，真实后端在前端 mock 全部完成后按第 7 节实施。

- 质量以可验证结果衡量：模块依赖可检查、公共基础可脱离健康业务运行、契约及异常路径可测试、性能有预算、运行故障可观测和恢复。技术选型说明收益、代价及适用边界，不能仅因旧项目或现有样板已使用就保留，也不以依赖数量衡量技术水平。
- 通用基础负责认证会话、权限与数据范围、错误结构、配置、审计基础、日志关联、构建测试和运行保障。健康业务负责采样、手表协议、阈值异常、处置规则和健康分析；通用代码禁止反向依赖健康领域对象。
- 后端首先采用模块化单体，一个 Spring Boot 应用内按业务职责隔离。模块公开查询和命令接口，禁止其他模块直接使用其内部 Mapper 或修改其表。通过模块结构测试约束循环依赖和内部访问；Spring Modulith/ArchUnit 的具体工具及兼容版本在实施时验证，未决定新增依赖。
- 页面七个业务域是产品组织，不机械映射为七个服务。工作台等组合查询通过业务模块的公开接口构成读模型，不能在前端拉取第一页数据冒充聚合。复杂绑定与事件动作保持事务和并发约束，普通 CRUD 不强制过度分层。
- OpenAPI 描述 API 契约，确定请求、响应、错误、空值、分页、时间和枚举。客户端类型可由契约生成，仍需运行时验证和语义测试；契约并不能证明统计正确。mock 与 HTTP 实现通过相同契约测试，生产构建不得静默启用 mock。
- Oracle 是本项目数据库，不承诺任意数据库无成本切换。数据访问与迁移集中管理，Oracle SQL 不泄露进前端或业务规则。保留既定 MyBatis 与迁移方式，新的工具采用前验证兼容性。
- 设备接入保留独立运行边界，依据连接规模、吞吐和故障隔离决定是否拆进程。Redis、队列、实时推送均须明确目的、背压、重试、幂等与故障处理，未选型能力不得在页面文案中写成既定架构。
- 可靠性门禁包含鉴权与数据范围、事务/幂等/版本冲突、乱序和重复输入、迁移与恢复、结构化日志和请求关联。后台统一保留 HTTP/业务错误含义；请求层返回类型化错误，页面负责上下文提示，避免底层与页面重复弹错。
- CI 分层执行类型检查、规则单元测试、契约测试、组件交互和关键端到端测试；浏览器断言必须验证结果，不能只确认 URL 或成功截图。真实 Oracle、设备容量、故障恢复在后端阶段实际验收，不用 mock 或其他数据库通过代替。
- 模板提取以实际模块复用和可移除性验证为依据，不先发布未经项目验证的公共框架。Agent 名称、型号与 IDE 调试方式属于协作配置，不成为业务代码依赖或唯一验收入口。

候选标准与工具依据：[OpenAPI](https://spec.openapis.org/oas/latest.html)、[MSW](https://mswjs.io/docs/)、[Spring Modulith 模块验证](https://docs.spring.io/spring-modulith/reference/verification.html)。MSW 为网络 mock 候选，不是已安装或强制选型；具体版本在实施批次固定。

## 3. 数据库具体怎么准备

先核实要部署的 Oracle 版本、地址、连接方式和可用功能，准备开发与测试使用的独立空间。环境允许时可以用容器；也可以连接专门的测试实例。

数据库建表和以后升级，都保存成带版本的脚本，方便在新环境重复执行。不能等用户点开业务页面时临时建表。

历史数据按测量时间建立查询索引并安排归档。是否分区、如何分区，在核实 Oracle 环境和数据量后决定，不耽误第一条业务流程。

地图计划使用 Oracle 的空间数据功能，正式使用前验证坐标、空间查询和索引。连接工具和数据库升级工具也要针对目标版本验证。

## 4. 什么时候报警，什么时候算处理完

### 报警规则需要写什么

写清监测哪项指标、适用于哪些人、上下限、异常持续多久、恢复正常多久、严重程度、处理时限、是否启用和规则版本。

数值在边界附近反复波动时，要有避免频繁报警和恢复的办法。具体参数需在规则发布前确定，这份计划不随意给出医学阈值。

同一次连续异常保留一个活动事件。短暂正常先观察，达到恢复条件后才标记稳定恢复。

### 两种状态分别保存

一是体征情况：正在异常、恢复观察中、已经稳定恢复或因数据不足无法判断。

二是工作人员处理情况：新事件、已经确认、已分派、处理中、处理完成、已经关闭，或经核实标记误报。

“体征恢复”不会自动抹掉事件和处理记录。“确认”表示工作人员已经确认这件事；“处理完成”需要有结果；“关闭”按约定条件结束处置。未建立独立的通知阅读记录前，不提供虚假的“已读”。

第一版动作和关闭规则按第 9 节执行，页面样板也模拟同一组规则。健康阈值、异常持续时间和恢复持续时间来自经确认并发布的规则配置；没有有效配置时显示未配置，不由生图或页面代码给出临床数值。

### 区分为什么产生事件

- 体征超限：心率、血氧等读数触发健康规则。
- 设备主动报警：手表主动上报求救、跌倒等信息。
- 趋势风险：一段时间内的变化触发趋势规则。

严重程度另外记录。SOS 只指设备主动求救，高危读数不能改名叫 SOS。设备报警不配置健康数值阈值，按已接入能力设置启停、严重度、处理时限和通知策略；未接入策略明确禁用。

## 5. 地图和其他功能怎么接上

地图原文件先检查坐标、单位和图层，转换后由人工核对巷道、井筒、工作面和文字，再发布一个可追查的版本。地图按可见范围和缩放程度加载，人员和事件作为单独图层显示。

任意一个人员点都要能找到设备、人员、来源和采集时间。没收到位置时，显示没有位置；旧位置显示时间，不能编造新坐标。

后续还要做入井规则与人工复核、报告生成和下载、设备控制与回执、原始消息查询、AI 数据引用、外部通知。每项操作都要有权限、结果和记录。

## 6. 可选的外部历史数据导入

仅在明确需要历史数据时实施，不作为核心建设前提。先确定保留哪些数据。从来源系统导出文件，隐藏或控制敏感信息，整理字段和编号，检查重复、缺失和无效值，再导入 Oracle 的临时检查区。核对无误后进入正式数据。

先搬组织、人员、设备和绑定，再搬健康记录与事件。每批记录来源、导出时间、文件校验信息、成功数、失败数、原因和编号对应关系；失败部分可以单独重做。

旧事件保留原意和来源，不能把过去没有记录的动作补成“已经做过”。新系统日常运行只连接 Oracle。

## 7. E0–E8：每一批做什么，如何验收

### E0：先让开发环境能稳定运行

准备 Java 21、固定构建工具和依赖版本（MyBatis、Flyway 与目标 Oracle 的兼容性在 E1 验证）、Oracle 开发测试环境，以及开发、测试、正式运行各自的配置。每次修改后自动检查程序能否构建和测试。

做完标准：换一套干净环境，照启动说明能运行；基础测试和页面构建稳定通过。

### E1：能登录、有权限、能保存基础数据

接入 Oracle 和带版本的建表脚本，完成账号、角色、查看范围、输入检查、错误提示、查询翻页和操作记录。页面与后台对需要交换的数据有统一说明。

做完标准：空库可以初始化；正常登录、拒绝越权、分页查询和重要操作留记录都能实际验证。

### E2：管好人员、部门、工种和手表

做好登记、搜索、筛选、翻页、绑定、解绑和导入检查。保存设备绑定历史，准备可重复使用的测试数据。

做完标准：从人能找到当前设备，从设备能查到历次绑定；修改操作有记录，错误导入有明确提示。

### E3：收到并保存真实健康数据

接设备通信，保存原始消息、有效读数和各指标最新值，处理重复、无效和乱序数据，显示在线与读数是否过旧。

做完标准：真实设备或明确标明的协议回放能稳定产生可查询的心率和血氧；重复与无效数据按规则处理，初步设备容量测试有结果。

### E4：让异常事件能够完整处理

完成规则版本、持续异常与恢复判断，支持确认、分派、处理、关闭和误报，保存处理时限、操作经过及待通知记录。

做完标准：连续异常、恢复观察和人工处理都能实际演示。页面刷新后状态仍在，每步操作都可追查。

### E5：统一查询、数字和自动更新

完善实时人员列表、总体摘要、小时与日汇总、个人历史趋势、实时通知与断线补发。为查询速度设定可检查的目标。第一条流程需要的最小查询和更新随 E3–E4 接入，这一批补齐完整能力。

做完标准：各处人数、异常人数、事件数、覆盖人数和数据时间对得上；总览查询不会每次翻遍所有历史记录。

### E6：接入真实地图和位置

保存地图版本、区域和图层，接当前位置及轨迹，支持按区域查询并显示位置是否过旧。

做完标准：地图上任意位置都可追查人员、设备、坐标、来源和时间；没有位置时如实显示。

### E7：补齐扩展功能

实现入井检查、报告、设备控制、原始消息查询、AI 和外部通知，按产品版本分批接页面。

做完标准：每项功能都有权限和操作记录，失败与未配置状态正确，设备或外部系统实际没执行时不能提示成功。

### E8：准备上线并演练故障恢复

进行容量、速度、权限和故障测试，试搬旧数据并对账，演练备份恢复、更新失败后的退回和运行告警。

做完标准：主要流程全部通过；正式账号和密码按部署要求配置；备份能恢复，数据搬迁可核对，故障和更新失败都有经过演练的处理办法。

## 8. 上线以后怎样保护数据和发现故障

正式环境不使用开发默认账号。健康信息和联系方式按权限查看，列表默认隐藏部分敏感内容；明文查看和重要操作留记录。日志不写密码、登录凭证或完整隐私数据。

报告注明数据范围、截止时间和用途。AI 提供辅助分析，不代替医学诊断。大文件通过授权入口访问，保存多久、何时删除和归档按上线要求确定。

系统要能查看设备连接、消息解析失败、保存失败、积压、读数过旧、事件产生与处理、通知失败、查询变慢和磁盘增长。日志需要轮换保存，异常达到约定条件要告警。

Oracle 使用经过验证的备份和恢复办法；地图、模型、报告和附件也要有版本和保留策略。备份必须真的试着恢复一次，程序和数据库更新失败时也要有可执行的恢复步骤。

## 9. 第一批页面和后台按同一份约定接起来

以下是要实现的约定，不是已有接口清单。开发时生成对应的类型和接口说明，前端演示数据与真实接口使用相同字段和动作；改变约定要同时更新页面材料、服务端和检查例子。

### 9.1 开始每一批需要什么

页面批次需要字段/操作契约、现有代码和可运行环境；创新布局另需用户确认的 Gemini 样板及交接材料，成熟列表无需先生成设计图。可以先用集中管理的虚构数据，不需要等待 Oracle 或真实手表。Grok 接手时必须保留样板的字段和状态约定，不得把 mock 数据直接当生产数据。

E0–E1 接数据库前需要：Oracle 版本与运行方式、可用开发测试实例、连接地址及服务名、测试账号权限。开发者先检查机器已有配置；缺少时由用户或部署负责人提供，密码使用环境变量或本机秘密配置，不写进文档和提交。未取得时可继续页面和独立业务规则测试，不能将其他数据库测试冒充 Oracle 验收。

E3 接手表前需要：设备型号、协议说明、真实或已验证的收发样本、能区分模拟器与真实设备的编号、佩戴及未佩戴样本。无法接真机时可先做明确标记的回放测试，记录尚未真机验收。

E4 发布正式健康规则前需要：业务方认可的指标阈值、持续时间、恢复条件和适用范围。规则须由业务方确认，配置来源与版本可追查。缺少时用测试专用规则检查程序，正式规则保持未配置。

### 9.2 第一版事件动作

体征情况与处理状态使用两个字段，不能互相覆盖。体征情况为异常、恢复观察、恢复、无法判断；设备和趋势事件不适用的恢复字段显示“不适用”。缺失数据不能自动标记恢复。

处理状态为新建、已确认、已分派、处理中、处理完成、已关闭、误报。新事件可以确认，也可以直接分派；直接分派表示接受任务但不补造独立的“确认”操作记录。已确认或已分派事件可以开始处理；未分派时先选择自己为处理人并保存分派记录。

新建、已确认、已分派和处理中可以重新分派，记录原人与新负责人，处理中重新分派仍保持处理中。处理中必须填写措施与结果才能完成；完成后按关闭规则关闭。新建到处理完成的非终结事件可由有权限的人填写理由并标记误报；已关闭与误报只读，第一版不支持重新打开。

关闭健康阈值事件时要求处理完成、有效数据已满足对应规则的恢复条件，并填写关闭说明；数据过旧、无法判断或仍在异常时保留待办并说明不能关闭的原因。设备主动报警和趋势事件要求处理完成且有核实依据与关闭说明，不伪造一个健康恢复状态。

同一人员、同一指标与适用规则形成的一次连续异常只保留一个异常过程。恢复条件满足后再次触发，建立新事件并关联前次过程，旧事件及其未完处置保留。人工误报只终结当前处置，不抹掉健康记录，也不停止规则监测；同一尚未结束的异常过程不因下一条消息立即重复建事件，后续数据继续关联原过程。严重度升级按规则记录变化并让值班人员可见，不能把误报当作永久忽略该人员。

查看、确认、分派、开始处理、完成、关闭和误报分别做服务器权限检查；接口返回当前用户允许的操作清单。页面隐藏按钮仅为使用方便，不承担最终授权。

### 9.3 首批查询和写入

复用当前认证方式：Cookie 保存 User-Token，请求头使用 satoken，响应外层保持 `{code,message,data}`。页面仍通过 `web/src/utils/request.ts` 访问 `/dev-api`，开发代理进入后端 `/api`。新增业务路径先在接口说明中建立，再实现；不假定已有接口。

- `GET /incidents`：按人员、部门、来源、严重度、处理状态、时间、我的待办/未分派/超时等条件查询，返回当前页、每页条数、总数和事件列表。
- `GET /incidents/summary`：使用与列表相同的授权范围和基础筛选，返回总待办、我的待办、高危未确认、未分派、已超时及统计时间。点击摘要后追加对应名单条件，不能从当前页计算摘要。
- `GET /incidents/{incidentId}`：返回事件信息、体征证据、人员设备、处理经过、当前记录版本和允许动作。
- `GET /incidents/assignees`：返回当前用户可以分派到的账号，支持搜索与分页，不暴露无权限部门账号。
- `POST /incidents/{incidentId}/actions`：提交动作类型、所见记录版本、请求唯一编号、目标处理人或措施/结果/原因。服务端检查动作、权限与版本，保存事件、处理经过和待发通知。

待办包含所有未关闭且非误报事件，包括处理完成但待关闭。我的待办按当前负责人，高危未确认按高危且新建，未分派按负责人为空，超时按非终结事件的 dueAt 与权威时钟计算；截止时间未配置不当作零或超时。摘要与名单使用同一口径。

人员简要信息可随详情返回；人员完整档案和设备管理分别在 E2 建立接口，不能由该详情接口扩大查询权限。

事件字段至少包括 incidentId、employeeId、employeeName、departmentId、departmentName、deviceId、location 及缺失原因、source、eventCode、severity、occurredAt、evidence、recoveryState、handlingState、assignee、dueAt、version、allowedActions。证据中的每个指标包含值、单位、measuredAt、有效性和过旧标记；时间线每项包含动作、执行人、时间、备注和结果。

编号按字符串交换，时间使用带时区的标准字符串；服务器内部统一时间基准，页面按 Asia/Shanghai 显示。允许为空的设备、位置、负责人和截止时间返回明确空值与原因；严重度排序由接口规定，不按中文标签拼音排序。

查询排序按严重度降序、发生时间升序、事件编号稳定排序。默认每页 20 条，允许 50 条；服务端限制最大页大小，确保前端和后端都不全量拉取后分页。

无权限返回明确拒绝；记录不存在返回未找到；版本过期或不允许的状态转换返回冲突；输入缺字段返回字段错误；依赖不可用返回服务失败。使用相应 HTTP 状态（401/403/404/409/400/503）并保留统一响应说明，不能全部伪装 HTTP 成功。发生冲突后重新查详情，保留尚未提交的备注供用户核对，不能自动覆盖提交。

同一个动作请求编号重试时返回已保存的结果，不新增第二条动作。事件版本检查、动作写入和待通知记录在同一次可靠保存中完成。成功后页面重新查询详情、列表和摘要；关闭事件导致最后一页为空时自动回到仍有效的上一页。

### 9.4 数据异常与实时更新的实施要求

设备带可靠消息编号时用设备与消息编号识别重复；无编号时保留原始消息、解析结果和接收顺序，结合测量时间与内容标记疑似重复，不用“读数相同”直接丢弃合法测量。无法确定设备测量时间时明确标记时间来源，不把服务器接收时间伪装成测量时间。

晚到的数据保存到历史，并按测量发生时的绑定关系归人；归属无法确定时进入待核查记录，不猜人员。旧数据不能覆盖时间更新的当前读数。规则计算处理乱序与重复时不能回拨已经确认的过程，也不能凭补传历史消息制造当前实时报警。

断报后显示读数过旧或无法判断；恢复观察不能靠没有新数据继续计时到“已恢复”。新有效数据到来后重新按规则检查。每项指标独立更新时间。

样板阶段用固定时钟验证通知与过期；真实接口阶段采用服务器提供的数据时间。页面默认 30 秒刷新，手动刷新与自动刷新不并发；关闭页面停止刷新，收到通知时合并短时间内的重复刷新请求。

容量与延迟目标统一见第 11 节。

数据库暂时不可用时，E3 必须实现有容量上限的可靠缓冲或明确拒收/失败处理，并演练短暂停机后的重放；不能用无限内存保存。先记录设备能否重传、实际峰值写入和允许停机时间，再计算缓冲容量并由部署方确认。通知历史保留时间、缓冲容量与恢复目标属于上线环境参数，在进入真实容量验收前填入配置记录；未定义或未通过恢复试验时不能进入 E8 上线通过状态。

### 9.5 从样板切到真实数据时的检查

页面使用统一的数据访问层，演示与真实接口提供同一份字段和错误结构。Gemini 样板和 Grok 的工程化阶段都可以使用集中管理的 mock adapter；演示功能只在明确的开发模式打开，正式运行缺接口就显示失败或未接入，不静默切回演示数据。计数、时间、按钮权限和处理状态以真实响应覆盖样板模拟。

按页面计划第 7 节重新验证相关操作。额外检查 Oracle 保存结果、服务重启后仍在、无权限请求被拒绝、两个窗口产生版本冲突、重复请求只保存一次，以及前端摘要和数据库查询对得上。

验收记录写明接口版本、数据来源、测试设备或回放方式、执行时间、测试结果与相关截图。完成对应真实业务验收后才标记为真实业务完成。

```text
com.xzkj.healthnext
```

## 11. 实时通知、容量与上线门禁

- 实时通知优先使用 SSE 告知页面重新查询；需要双向通信时再评估 WebSocket。业务变更与 Outbox 在同一事务保存，投递失败重试；使用事件编号去重和 Last-Event-ID 补发，超出保留窗口执行全量重新同步。通知范围仍须校验用户权限，不向所有连接广播敏感信息。
- 全量筛选、摘要和分页在服务端共用授权与统计口径。异常人数按人去重，事件数独立；返回单位、时间窗口、覆盖人数、逐指标采集时间、历史样本数和聚合方式。当前异常下钻与快照使用相同窗口、新鲜度及规则，不能用另一时间范围的历史记录解释实时人数。
- 设备接入除首批心率/血氧外，逐步覆盖登录、心跳、血压、体温及主动报警。协议解析与规则分离；已验证 APHP 未佩戴占位血氧不当有效值，错误零电量不得覆盖有效电量。每种型号用实际协议样本确认，不把某一型号的异常推广成通用常量。
- E3 先验证 1000 台基础负载，按实际需求评估 5000 台；记录发送频率、峰值、硬件和数据范围。常用查询 p95 ≤ 1 秒、已保存事件正常网络下 5 秒内可见为待验证目标，不能写成已有性能。
- CI 分层验证正常流程、规则/状态机、权限范围、契约、并发幂等、绑定换人、重复乱序、无效/未佩戴、断报、Oracle 初始化/升级及查询；真实数据库和协议回放/真机结果分别标注。
- 上线前确认数据保留、通知补发窗口、缓冲容量、允许丢失量与恢复时间目标。演练数据库慢/短暂停机、积压恢复、通知中断、重复消息、迁移对账和更新失败恢复；容量无上限、恢复目标未定或恢复试验未过，均不能标记 E8 完成。
- Oracle 备份与恢复可使用 RMAN，配合目标环境归档日志验证。隔离测试环境可按条件使用 Testcontainers，但不能以其他数据库测试代替目标 Oracle 验收。地图、模型、附件和报告同步制定备份与保留策略。
