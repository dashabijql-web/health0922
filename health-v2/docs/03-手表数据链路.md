# 03 手表数据链路

依据：仓库根目录的《智能手表开发协议.docx》。

## 一、协议

所有数据包格式：`IW` + 协议号 + 参数 + `#`。手表发给服务器的协议号以 `AP` 开头，服务器发给手表的以 `BP` 开头，数字相同表示"包与它的响应"（`AP00` 登录，服务器回 `BP00`）。中文用 Unicode 编码。

协议的两个特点决定了设计：

1. **只有登录包 `AP00` 带 IMEI**（设备号，15 位），之后的包都不带，服务器要记住"这条连接是哪块表"。
2. **体征包没有时间字段**，采集时间只能取服务器收到的时间。

### 处理哪些包

上行包分两种：手表**主动上报**的（登录、心跳、体征、报警），服务器要回复；手表对服务器指令的**确认**（如 `APXL`），服务器不再回复，否则会把 `BPXL` 这类测量指令又发回去。

| 协议号 | 含义 | 内容 | 用途 | 回复 |
| --- | --- | --- | --- | --- |
| `AP00` | 登录 | IMEI | 建立连接与手表的对应关系 | `BP00` 带授时（见下） |
| `AP03` | 心跳 | 电量、步数、翻滚次数 | 记录电量和步数 | `IWBP03#` |
| `AP49` | 心率 | 心率 | 入库 | `IWBP49#` |
| `AP50` | 体温 | 体温、电量 | 入库体温；电量不采用 | `IWBP50#` |
| `APHT` | 心率+血压 | 心率、收缩压、舒张压 | 入库 | `IWBPHT#` |
| `APHP` | 综合 | 心率、收缩压、舒张压、血氧、血糖、体温 | 入库（血糖不用） | `IWBPHP#` |
| `AP10` | 报警 | 定位、状态串、报警代码等 | 生成设备报警事件 | `IWBP10#`（地址内容留空） |
| `AP01` `AP02` | GPS/基站定位 | | 井下无 GPS，不使用 | `IWBP01#` / `IWBP02#` |
| `APXL` `APXY` `APXZ` `APXT` `AP33` `AP86` `AP87` | 指令确认 | 指令流水号 | 只记日志"手表已确认"，数值以随后的体征包为准 | 不回复 |
| `AP07` | 语音上行 | 含二进制音频 | 不使用 | 不回复（切包见第二节） |
| 其他 | | | 计数，不断开 | 不回复 |

**`AP10` 的格式**：协议号后面直接接定位串（没有逗号），之后按逗号分段：`IWAP10<日期 yyMMdd+定位+状态串>,460,0,9520,3671,00,zh-cn,00,<WIFI>#`。按逗号拆开后，第 6 段（下标 5，例子里的 `00`）是报警代码。不到 6 段的包按格式错误丢弃；不在下表里的报警代码不生成事件，计入 `health.watch.dropped{reason=unknown_alarm}` 并记一条日志。

登录回复带时间：

```text
收到：IWAP00353456789012345#
回复：IWBP00,20260924093000,8#     (UTC 零时区时间 yyyyMMddHHmmss，8 是东八区)
```

### 心跳里的电量

`AP03` 第一个参数是 14 位字符，如 `06000908000102`：GSM 信号（0–2 位）、卫星数（3–5 位）、**电量（6–8 位，`080` 即 80%）**、保留（9 位）、设防状态（10–11 位）、工作模式（12–13 位）。

电量只用 `AP03` 的。`AP50` 也带电量，但可能错报 `0`，所以不采用。任何来源的电量为 `0` 都不覆盖已有的有效值，也不触发低电报警。

### 报警包 `AP10` 的类型

| 代码 | 含义 | 处理 |
| --- | --- | --- |
| `01` | SOS | 计入大屏"SOS 告警" |
| `05` `06` | 跌倒 | 计入大屏"跌倒告警" |
| `02` `03` `04` `08` `13` `14` `15` `20` | 低电、脱落、佩戴提醒、房颤、拆卸、红外 | 记为设备事件，不计入六类告警，在大屏"设备事件"里展示（`05` 第四节）；房颤归哪一类见 `00` 第 18 项 |
| `00` | 无报警 | 忽略 |

事件代码（`ALERT_EVENT.CODE`）：`01` → `SOS`；`05`/`06` → `FALL`；`02` → `LOW_BATTERY`；`03` → `WEAR_OFF`；`04` → `WEAR_REMIND`；`08` → `AFIB`；`13`/`14`/`15` → `REMOVED`；`20` → `INFRARED`。
严重程度（`SEVERITY`）：1 提示、2 一般、3 严重。SOS、跌倒为 3；其余设备事件为 1；体征越界取阈值那一行的 `SEVERITY`（建表时都是 2）。

## 二、连接与会话

```text
手表 ──TCP──▶ Netty（9001）: ① 按 # 切包  ② 解码
                  ▼
        会话：连接 ⇄ IMEI；卡编码按包查绑定，③ 校验数据是否有效
                  ▼
        有界线程池 ──▶ Redis 缓冲
```

- **切包**：TCP 是字节流，一次可能收到半个包或多个包。按 `#` 切开，不完整的留到下次拼接。单包超过 8 KB 丢弃并断开连接。例外是 `AP07`：它带二进制音频，里面可能出现 `#`，所以识别到 `IWAP07` 时按它的长度字段整段读完再丢弃。
- **会话**：登录后只记"连接 → IMEI"。没登录就发其他包的连接，数据丢弃并关闭连接；连上 30 秒内不发 `AP00` 也关闭。同一 IMEI 再次登录，新连接替换旧连接；同一条连接先后用两个不同的 IMEI 登录，关闭连接。IMEI 不是 15 位数字的登录包，关闭连接。10 分钟没有任何数据的连接主动关闭。格式不对的包（不以 `IW` 开头、协议号不合法）丢弃并计数，不断开连接。
- **卡编码**：不存在会话里。每个包处理时，从"IMEI → 卡编码"绑定缓存里查，收到时就把当时的卡编码写进这条数据，之后不再改。缓存每 60 秒从 `DEVICE` 表刷新一次，后台修改绑定时立即刷新。这样手表换绑后，新数据马上记到新的人名下，不用等手表重连。`DEVICE.STATUS = 0`（停用）的表按未登记处理。
- **资源上限**：最多同时 `WATCH_MAX_CONNECTIONS` 个连接（默认 2000），超过的新连接直接关闭。
- **认证**：协议本身没有认证，任何能连上 9001 的设备都能用任意 IMEI 登录，挤掉真的手表。部署时用防火墙只放行手表所在网段（`08` 阶段 7）。
- **设备登记**：

| 手表 | 体征、心跳 | `AP10` 的 SOS、跌倒 |
| --- | --- | --- |
| 已登记、已绑定 | 正常入库 | 生成事件，带卡编码 |
| 已登记、未绑定 | 体征不入库（体征表以卡编码为准），只计数；心跳照常更新设备的在线时间和电量 | 照常生成事件，卡编码为空、记设备号，大屏上可见（见 `05`） |
| 未登记 | 回复登录（免得手表反复重连），数据不入库，只计数、限频记日志（每块表 10 分钟一条） | 同上 |

未登记、未绑定的表登录后也照常下发配置和测量指令：后台登记或绑定后，1 分钟内（绑定缓存刷新）数据就开始入库，不用等手表重连。
未绑定的表不知道是谁，所以体征不入库，也**不判断体征越界**（不产生 `THRESHOLD` 事件）；只有 `AP10` 的报警照常生成事件。
**绑定的办法（`00` 第 2 项，默认做法）**：后台做出来之前用脚本写 `DEVICE` 表。模拟手表用 `tools/watch-simulator/sim.py bind`（见第七节）；真实手表到阶段 7 联调时，按同样的写法准备一份"IMEI → 卡编码"清单导入，阶段 8 的后台再提供 Excel 批量导入。
- **线程**：Netty 线程只收发和切包，不做数据库操作。后续处理交给有界线程池（线程名前缀 `watch-data-`，默认 4 个线程、队列 10000，队列满时由提交者自己执行，起回压作用）。采集时间在 Netty 线程收到包时就定下，线程池里谁先处理不影响时间。
- **回复在 Netty 线程里立即发**，不等数据处理完：手表主动上报的包（登录、心跳、体征、报警、定位）回复；指令确认（`APXL` `APXY` `APXZ` `APXT` `AP33` `AP86` `AP87`）、语音、未知协议号不回复。

## 三、数据有效性

手表没戴好时仍会上传，值是 `0` 或占位值：

| 情况 | 处理 |
| --- | --- |
| 心率、血压、血氧、体温为 `0` 或空 | 丢弃该指标（`APHP` 里没测的项本来就留空，不算丢弃、不计数） |
| `APHP` 中出现 `0,0,0,95,0.0,0.0`（血氧 `95` 是未佩戴占位值） | 整个包丢弃 |
| 超出合理范围 | 丢弃 |

合理范围只用来筛掉明显错误，不是预警阈值：心率 30–220、血氧 50–100、体温 30.0–45.0、收缩压 60–260、舒张压 30–160、电量 1–100。血压要收缩压、舒张压都有效才算一条。数值按一位小数保存（四舍五入）。

被丢弃的数据按原因累计到指标 `health.watch.dropped`，页面不展示。原因标签：`zero`（0 或空）、`placeholder`（`APHP` 未佩戴占位包）、`out_of_range`、`malformed`（格式不对）、`unbound`（未绑定的表的体征）、`unregistered`（未登记的表的数据）、`not_logged_in`、`oversize`（超过 8 KB）、`unknown_alarm`、`connection_limit`（连接数已满）。

## 四、预警

数据通过有效性检查后立刻判断，不等写库。事件量小，又要尽快出现在大屏上，所以直接写 `ALERT_EVENT`，不走缓冲。

| 类型 | 来源 | 例子 |
| --- | --- | --- |
| 体征越界 `THRESHOLD` | 服务器按阈值判断 | 心率过高、血氧过低 |
| 设备报警 `DEVICE` | 手表 `AP10` 主动上报 | SOS、跌倒 |

SOS 只来自 `AP10` 的 `01`。

**阈值按岗位类别分**：干重活的人心率本来就高，所以不同岗位用不同的正常范围。做法是把厂家的工种归成几个**岗位类别**（如采掘、机电、运输、通风安全、管理），每个类别一套阈值：

1. 由卡编码查到这个人的工种（`POS_PERSON.JOB_KIND`）；
2. 由工种查到岗位类别（`JOB_KIND_GROUP`）；工种没归类、工种为空，都用默认类别 `DEFAULT`（未绑定的表不判断越界，见第二节）；
3. 取这个类别该指标的阈值（`ALERT_RULE`）；这个类别没配这一项，就用 `DEFAULT` 的。

判断时用到的岗位类别记进事件（`ALERT_EVENT.RULE_GROUP`），事后能查到当时按哪套标准判的：记的是**实际用的那一行阈值**所属的类别，这个类别没配这项、用了 `DEFAULT` 的，就记 `DEFAULT`。人员工种和归类表跟阈值一起每分钟刷新进内存。

判断规则：值 < `LOW_LIMIT` 算偏低，值 > `HIGH_LIMIT` 算偏高（等于不算），为空的一侧不判断；`ENABLED = 0` 的阈值不产生事件。血压的收缩压、舒张压分别判断，各自是一条事件，`VAL_TEXT` 都记成 `152/98`。事件代码 = 指标前缀 + `_LOW`/`_HIGH`：`HR`、`SPO2`、`TEMP`、`BP_SYS`、`BP_DIA`。

**阈值**存 `ALERT_RULE`，不写死在代码里，上线后随时可以改：启动时读入内存，之后每分钟重新读一次，改完最多 1 分钟生效。阶段 8 的后台提供修改页面，在那之前用 SQL 直接改表。通过后台修改时写操作日志（`ALERT_RULE_SET`，记改前改后的值）；直接改表不会留日志，所以后台做好后只通过后台改。

下面是建表时写入的 `DEFAULT` 类别初始值，目前是开发占位值。上线前请矿上医务人员定下岗位类别、各类别的阈值（`00` 第 3、22 项）：

| 指标 | 偏低 | 偏高 |
| --- | --- | --- |
| 心率（次/分） | < 50 | > 120 |
| 血氧（%） | < 90 | — |
| 体温（℃） | < 35.0 | > 37.3 |
| 收缩压（mmHg） | < 90 | > 140 |
| 舒张压（mmHg） | < 60 | > 90 |

**去重**：同一个人（没绑定时按设备号）、同一事件代码，距**上次发生**（`LAST_OCCURRED_AT`）不到去重间隔，就不新建事件，只更新最近发生时间和次数。所以一段持续的异常只算一条事件，而不是每分钟一条。

- 间隔：体征越界 30 分钟；SOS 和跌倒 2 分钟（重复包多半是同一次事件）；低电、脱落等其他设备事件按体征越界的 30 分钟（它们是持续状态）。可配置，见 `01` 配置表。
- 去重期间只更新 `LAST_OCCURRED_AT`（取更晚的）和 `OCCUR_COUNT`，`VAL_TEXT` 保留第一次的值。
- **事件不跨天**：过了 0 点再发生，算新的一条。这样"今天""本月"的事件数口径清楚。
- 去重以 `ALERT_EVENT` 表为准：启动时把当天仍在间隔内的事件读进内存；内存里记着的那条在表里已经不在了（被人删了），就新建一条。同一个人的判断和写入按卡编码（或设备号）加锁串行，避免两个线程同时新建。
- 写事件失败（数据库连不上）只记日志，不影响体征进缓冲；这次的事件就丢了，下次再越界时照常判断。

## 五、存储

约 200 块表、每块每分钟 1 条，一天约 30 万条，一条条写库会拖慢系统，所以先放 Redis 再成批写。

每条指标数据在收到时就带上：唯一编号 `MSG_ID`（进程内生成，毫秒时间戳 × 1000 + 序号）、IMEI、卡编码、采集时间。

```text
有效数据 ──▶ hv2:watch:buf ──(每 5 秒，Lua 脚本原子地移走最多 1000 条)──▶ hv2:watch:processing
                                                                        │ 一个数据库事务：
                                                                        ├─ 插入 HEALTH_RECORD（MSG_ID 已存在的跳过）
                                                                        ├─ 更新 HEALTH_LATEST（只接受更新的时间）
                                                                        ├─ 更新 STEP_DAILY（覆盖为最新累计，见下）
                                                                        ├─ 更新 DEVICE 的电量（只接受更新的时间）
                                                                        └─ METRIC_COUNTER 加上本批实际新插入的条数
                                                                        ▼
                                                            提交成功后，从 processing 删除这一批
```

"原子地"指"移出 buf"和"放进 processing"一步完成，中间崩溃也不会两边都没有。

- 每 5 秒一轮。一轮里先处理 `processing` 里上次留下的一批，再从 `buf` 移一批写一批；一批满 1000 条就接着移下一批，直到 `buf` 移空，所以积压再多也不会越积越多（压测时每秒上千条也能跟上，见第九节）。
- 一批里同一个人同一指标有多条时，`HEALTH_LATEST` 只写最新的一条；采集时间是同一秒时，`MSG_ID` 大的算新。
- 采集时间写库时舍到秒（表里是 `TIMESTAMP(0)`）；`MSG_ID` 在收到时按毫秒生成，所以同一秒的数据也不会撞号。
- `HEALTH_RECORD` 用 JDBC 批量 `MERGE` 写入，按逐条返回的行数（1 插入、0 已存在）累加计数；驱动拿不到逐条行数时整批报错回滚，宁可不写也不多算。
- 最后在线时间不在这个事务里：它在内存里随每个包刷新，每轮开头把变化过的一起写进 `DEVICE.LAST_SEEN_AT`（只接受更晚的时间），写失败下一轮再写。

每一步写入都是"重复做一遍结果不变"的：流水按 `MSG_ID` 去重，最新值、步数、在线时间只接受更新的时间，计数只加真正新插入的条数。所以同一批数据被处理两次，既不会重复入库，也不会重复计数。

| Redis key | 类型 | 用途 |
| --- | --- | --- |
| `hv2:watch:buf` | 列表 | 待写库的数据 |
| `hv2:watch:processing` | 列表 | 正在写库的一批，提交成功后删除 |
| `hv2:watch:dead` | 列表 | 写不进库的单条数据，人工排查 |
| `hv2:watch:step:<imei>` | 哈希 | 步数计算状态（见下） |

- **写库失败**：整个事务回滚，先看是哪种错：
  - 数据库暂时不可用（连不上、超时、连接断开）：整批留在 `processing`，下一轮原样重试，**不拆**，免得数据库一停就把所有数据拆进死信；
  - 数据本身写不进（如数值超出列的精度）：把这一批对半拆开分别写，还失败的继续拆，直到找出写不进去的单条。单条重试 3 次仍失败，移进 `dead` 并记错误日志，其余数据照常入库；
  - 不是数据库报的错（程序问题）：整批留着等排查，不拆。
  - 缓冲里解析不了的内容（不是合法 JSON、缺字段）直接进 `dead`。
  - 日志只记 `MSG_ID` 和 Oracle 错误码（如 `ORA-01438`），不记错误信息原文：Oracle 的错误信息里会带着写入的值，而日志不能出现体征数据（`01`"安全"）。
- **进程崩溃或重启**：启动时先处理 `processing` 里留下的批次，再处理 `buf`。
- **正常停止**：先关闭 9001（不再收新数据），再等线程池把已收到的包处理完（最多 10 秒），最后一轮接一轮把缓冲写完（最多 20 秒）。写不完的留在 Redis，下次启动接着写；降级为内存队列时就靠这一步写完。
- **Redis 不可用**：降级为进程内的有界内存队列（上限 10000 条），照常批量写库；队列满了丢弃最旧的并计数。进程崩溃时，内存队列里的数据会丢，这是降级期间接受的代价。Redis 恢复后，先写完内存队列，再切回 Redis。
  - 判断方法：往 Redis 放数据失败一次就切到内存队列；之后每轮写库时 `PING` 一下，通了、且内存队列写完了才切回。切换的那一下要等 Redis 超时（3 秒），这几秒的包在线程池里排队，不会丢。
  - Redis 停下之前已经放进 `buf`、还没写库的数据留在 Redis 里（Redis 自己的持久化保存着），等 Redis 恢复后照常写库，不会丢；这期间库里这几条会晚到。实测见第九节。
- **最新值**不放 Redis，放在 Oracle 的 `HEALTH_LATEST`（每人每指标一行），大屏直接查它，Redis 重启不受影响。
- key 前缀可配置（`hv2.watch.buffer.key-prefix`，默认 `hv2:watch:`，必须以 `hv2:` 开头）；后端测试用 `hv2:test:watch:`，不碰运行中的数据。

**在线** = `DEVICE.LAST_SEEN_AT` 在在线窗口内（默认 20 分钟，见 `01` 配置表）。每个上行包（登录、心跳、体征、报警、指令确认都算）都在内存里刷新这块表的最后上行时间，每轮写库时一起写进 `DEVICE`。手表每项体征约每 4 分钟才测一次（见下节），窗口要明显长于测量周期。只算已登记、启用的表；启动时从 `DEVICE.LAST_SEEN_AT` 读回，重启后在线数不会从 0 开始。

**步数**：`AP03` 里的步数是手表上的累计计数器，**不按天归零**，到上限后从 0 重新计（协议示例是 9999，也可能是 65535）。今天的步数 = 今天各次读数的增量之和。

增量在**收到心跳时**就算好，不在写库时算，免得重试、乱序打乱先后。每块表在 `hv2:watch:step:<imei>` 里存：上次读数、上次读数时间、卡编码、日期、今天累计，用 Lua 脚本原子更新：

| 情况 | 增量 |
| --- | --- |
| 没有上次读数（新表、首次上线、状态丢失） | 0，只记下这次读数作起点 |
| 卡编码和上次不同（换绑） | 0，重新作起点 |
| 这次读数时间早于上次（乱序） | 忽略这次读数 |
| 新读数 ≥ 上次 | 差值 |
| 新读数 < 上次（计数器回绕或手表重启） | 新读数本身（回绕前的一小段会少算，可接受） |

- **跨天**：0 点后的第一次读数，"今天累计"从 0 开始，但"上次读数"保留，照常算增量。0 点前最后一次读数到这次之间走的步数，算进新的一天。
- **没有状态时的起点**：Redis 里没有这块表的状态（新表、Redis 丢了数据），或状态里的卡编码和这次不同（换绑），就从 `STEP_DAILY` 取这个人最近一天（不晚于今天）的一行作起点：那一行是今天的，"今天累计"接着它算；"上次读数"只有那一行来自同一块表（`STEP_DAILY.DEVICE_IMEI`）才用，否则这次读数只作起点。这样 Redis 丢了状态、换绑、换表，当天步数都不会变少，也不会把整个计数器读数当成增量。
- 状态在 Redis 里保留 3 天（跨天要用前一天最后的读数）。
- 算好的"今天累计"随心跳数据进缓冲，写库时直接**覆盖** `STEP_DAILY`（只接受更晚的读数时间），重复写不会重复累加。
- Redis 不可用时，改用进程内的状态，算法和 Lua 脚本相同（测试里两边跑同一组用例），没有状态时同样从 `STEP_DAILY` 取起点；结果也只写 `STEP_DAILY`。Redis 恢复后丢掉进程内的状态，改回 Redis 里的：两边记的"今天累计"和"上次读数"是配对的，接着算结果一样。

## 六、服务器下发测量指令

手表不会自己按需测量。

登录成功后：

1. 下发 `BP33`，工作模式设为正常（1）：`IWBP33,<IMEI>,<流水号>,1#`。
2. 下发 `BP86`、`BP87`，关闭手表自己的测量周期，避免两套调度重叠：`IWBP86,<IMEI>,<流水号>,0,1#`（`BP87` 同）。参数沿用老项目在真实手表上收到过确认的写法。
3. 每 60 秒给每块表下发一项测量，按顺序轮换，不同时启动多个传感器：`BPXL`（心率）→ `BPXY`（血压）→ `BPXZ`（血氧）→ `BPXT`（体温）→ 回到心率。每项指标约每 4 分钟测一次；节奏由 `WATCH_MONITORING_REFRESH_SECONDS` 配置（默认 60），周期同比例变化。

时间：登录回复立即发；`BP33`、`BP86`、`BP87` 依次在第 0、1、2 秒发；第 3 秒发第一条测量，之后每 60 秒一条。指令流水号是全局递增的 6 位数，到 `999999` 后从 `000001` 重新开始。连接断开时停止下发。

```text
服务器发：IWBPXL,353456789012345,080835#    (IMEI，指令流水号)
手表回：  IWAPXL,080835#                     (只是确认收到，服务器不回复)
随后手表发：IWAP49,68#                        (这才是真实心率)
```

## 七、手表模拟器（`tools/watch-simulator/`）

Python（`asyncio`），模拟 N 块手表（默认 200），一次只能启动一个实例：

- 每块表一个 IMEI，连接 `127.0.0.1:9001`，先发 `AP00` 登录；收到测量指令就回确认，再发对应数据包；定时发 `AP03`（默认每 60 秒；电量缓慢下降，到 20% 时发一次 `AP10` 低电报警；步数累加并在上限处回绕，默认 65535）。
- 数值符合真实分布（每次测量有 1% 的概率出现偏高偏低的值、1% 的概率按没戴发 `0`），并能用 `send` 命令制造场景：指定心率/血氧/体温/血压、SOS、跌倒、任意报警代码、没戴、掉线重连、改计步器读数、手表重启（计步器归零）、立即测量、发任意原始包。
- **IMEI 与绑定**：第 i 块表的 IMEI 是 `8699` + i 补足 11 位（如 `869900000000001`），绑定定位文件生成器的第 i 个假人（`sim.py people --json`，卡编码 `62082300920390001` 起）；超出假人数量的表登记但不绑定。`--unregistered K` 另外模拟 K 块没登记的表（`8698` 开头）。默认 200 块表、120 个假人：120 块已绑定、80 块已登记未绑定。
- `sim.py bind` 把这份对应写进 `DEVICE` 表（经 Docker 容器里的 `sqlplus`，密码从标准输入传入，不出现在命令行上；`--test` 写测试用户），人员表里没有的人不绑定；`sim.py swap 1 2` 对调两块表绑定的人，用来演示在线改绑定。
- **测量指令的回应**（`10` 第 3 项在模拟器里的做法，真实手表到阶段 7 再核对）：

| 收到 | 回 | 随后发 |
| --- | --- | --- |
| `BPXL` | `APXL,<流水号>` | `AP49,心率` |
| `BPXY` | `APXY,<流水号>` | `APHT,心率,收缩压,舒张压` |
| `BPXZ` | `APXZ,<流水号>` | `APHP,,,,血氧,,,,,,,,,`（只填血氧，其余留空；协议允许"无值则留空"） |
| `BPXT` | `APXT,<流水号>` | `AP50,体温,0`（电量报 `0`，和真实手表错报的一样，后端不采用） |
| `BP33` / `BP86` / `BP87` | `AP33,<流水号>,1` / `AP86,<流水号>` / `AP87,<流水号>` | — |

  没戴时：`AP49`、`APHT` 发 `0`，`APHP` 发未佩戴占位包 `0,0,0,95,0.0,0.0`，`AP50` 发 `0.0`。
- 计步器读数和电量存在 `runtime/watch-sim/state.json`，模拟器重启后接着用（真实手表不会因为服务器重启而归零，否则会被当成"手表重启"）。每 30 秒把统计写进 `runtime/watch-sim/stats.json`：每块表本次运行发出的有效体征条数、走的步数，用来和库里的数据对账。
- `sim.py once --imei <IMEI> <包>...` 单独连一次，打印服务器的全部回复，用来看回复规则。

```text
python3 tools/watch-simulator/sim.py bind                 # 写 DEVICE（后端 60 秒内生效）
python3 tools/watch-simulator/sim.py run                  # 200 块表；--watches 1000 --unregistered 2 等
python3 tools/watch-simulator/sim.py send 3 hr 125        # 第 3 块表之后的心率都是 125（hr off 恢复）
python3 tools/watch-simulator/sim.py send 150 sos         # 未绑定的表发 SOS
python3 tools/watch-simulator/sim.py send unreg1 sos      # 未登记的表发 SOS
python3 tools/watch-simulator/sim.py send 20 unworn on    # 第 20 块表没戴
```

## 八、指标

通过 Spring Actuator 暴露，名称以 `health.` 开头：

- `health.watch.connections`：当前连接数。
- `health.watch.online.count`：在线手表数，口径同上面的"在线"。
- `health.watch.packets`：收包数，按协议号。
- `health.watch.dropped`：丢弃数，按原因。
- `health.buffer.size`：缓冲积压。
- `health.buffer.flush.duration`：每批写库耗时。
- `health.buffer.split` / `health.buffer.dead`：拆批次数、进死信条数。
- `health.buffer.memory.dropped`：降级队列满时丢弃的条数。
- `health.alert.created`：新预警数，按来源（`src`）和大屏分类（`category`）。
- `health.summary.duration`：重算一天日汇总的耗时（`04` 的 `HEALTH_DAILY_SUMMARY`）。

## 九、实测（阶段 2，本机）

环境：MacBook 本机，Oracle Free 26ai（Docker 容器 `local-oracle-free`）、Redis 8.10，后端和模拟器在同一台机器上。数字只说明量级，上线服务器到阶段 7 再测一次（`10` 第 17 项）。

| 项目 | 做法 | 结果 |
| --- | --- | --- |
| 200 块表稳定运行 1 小时 | 200 块登记的表（120 块绑定）+ 2 块未登记，默认节奏（每 60 秒一项测量、60 秒一次心跳），每分钟采样一次 | 连接 202、在线数 200 始终不变；`health.buffer.size` 最大 4；每分钟写 11–12 批，每批平均 9 ms（头 10 分钟 8.8 ms，末 10 分钟 9.3 ms），最慢一批 85 ms |
| 正常停止 | 模拟器照常发数据时停止后端 | 日志"停止前缓冲已全部写库"，Redis 的 `buf`、`processing` 为空；这一小时里 120 块绑定的表发出的有效体征 9273 条，库里新增正好 9273 条；每块表最后一次计步器读数都已进 `STEP_DAILY` |
| 降级为内存队列时正常停止 | 停掉 Redis，1 分钟后停止模拟器、再停止后端 | 新增 475 条 = 模拟器发出的 475 条；12 块表停 Redis 前的最后一次心跳留在 Redis 的 `buf` 里，Redis 恢复后写入，步数合计和模拟器实际走的步数一致（11835 步） |
| `kill -9` | 先关掉定时写库让 Redis 里积 13660 条，再启动后端，在第 3 批写库中途（`processing` 里有 1000 条）`kill -9`，再启动 | 启动后先处理"上次留下的一批 1000 条"；最终新增 13064 条 = 模拟器发出的 13064 条，没有重复的 `MSG_ID`，`METRIC_COUNTER` 合计 = 表里总条数，步数合计和模拟器走的步数一致 |
| 停 Redis | 200 块表运行中停掉 Redis 1 分钟再启动 | 连接数不变；停机期间照常写库（1 分钟新增 114 条）；恢复后日志"Redis 已恢复，手表数据切回 Redis 缓冲"，没有重复行 |
| 坏数据 | 往运行中的 `buf` 放一条心率 99999999 的数据 | 这一批拆了 6 次，只有这一条进 `dead`（日志只有 `ORA-01438`），同批其余数据正常入库 |
| 1000 块表（`10` 第 17 项） | 测试用户里造 1000 个假人、1000 块已绑定的表；测量指令改为每秒一次（正常的 60 倍），30 分钟造出一天多的数据量（1000 块表一天约 180 万条：每块表每 4 分钟 5 条） | 写库跟得上：每秒约 1250 条，缓冲最多积压 316 条。日汇总重算"今天"的耗时和当天条数大致成正比，约每千条 1.2 毫秒：36 万条 0.35 秒、110 万条 1.2 秒、185 万条 2.2 秒、222 万条 2.5 秒（都是一边大量写入一边重算），远小于 5 分钟的间隔 |
