# 03 手表数据链路

依据：仓库根目录的《智能手表开发协议.docx》。

## 一、协议

所有数据包格式：`IW` + 协议号 + 参数 + `#`。手表发给服务器的协议号以 `AP` 开头，服务器发给手表的以 `BP` 开头，数字相同表示"包与它的响应"（`AP00` 登录，服务器回 `BP00`）。中文用 Unicode 编码。

协议的两个特点决定了设计：

1. **只有登录包 `AP00` 带 IMEI**（设备号，15 位），之后的包都不带，服务器要记住"这条连接是哪块表"。
2. **体征包没有时间字段**，采集时间只能取服务器收到的时间。

### 处理哪些包

上行包分两种：手表**主动上报**的（登录、心跳、体征、报警），服务器要回复；手表对服务器指令的**确认**（如 `APXL`），服务器不再回复，否则会把 `BPXL` 这类测量指令又发回去。

| 协议号 | 含义 | 内容 | 用途 | 回复 |
| --- | --- | --- | --- | --- |
| `AP00` | 登录 | IMEI | 建立连接与手表的对应关系 | `BP00` 带授时（见下） |
| `AP03` | 心跳 | 电量、步数、翻滚次数 | 记录电量和步数 | `IWBP03#` |
| `AP49` | 心率 | 心率 | 入库 | `IWBP49#` |
| `AP50` | 体温 | 体温、电量 | 入库体温；电量不采用 | `IWBP50#` |
| `APHT` | 心率+血压 | 心率、收缩压、舒张压 | 入库 | `IWBPHT#` |
| `APHP` | 综合 | 心率、收缩压、舒张压、血氧、血糖、体温 | 入库（血糖不用） | `IWBPHP#` |
| `AP10` | 报警 | 定位、状态串、报警代码等 | 生成设备报警事件 | `IWBP10#`（地址内容留空） |
| `AP01` `AP02` | GPS/基站定位 | | 井下无 GPS，不使用 | `IWBP01#` / `IWBP02#` |
| `APXL` `APXY` `APXZ` `APXT` `AP33` `AP86` `AP87` | 指令确认 | 指令流水号 | 只记日志"手表已确认"，数值以随后的体征包为准 | 不回复 |
| `AP07` | 语音上行 | 含二进制音频 | 不使用 | 不回复（切包见第二节） |
| 其他 | | | 计数，不断开 | 不回复 |

**`AP10` 的格式**：协议号后面直接接定位串（没有逗号），之后按逗号分段：`IWAP10<日期+定位+状态串>,460,0,9520,3671,00,zh-cn,00,<WIFI>#`。按逗号拆开后，第 6 段（下标 5，例子里的 `00`）是报警代码。

登录回复带时间：

```text
收到：IWAP00353456789012345#
回复：IWBP00,20260924093000,8#     (UTC 零时区时间 yyyyMMddHHmmss，8 是东八区)
```

### 心跳里的电量

`AP03` 第一个参数是 14 位字符，如 `06000908000102`：GSM 信号（0–2 位）、卫星数（3–5 位）、**电量（6–8 位，`080` 即 80%）**、保留（9 位）、设防状态（10–11 位）、工作模式（12–13 位）。

电量只用 `AP03` 的。`AP50` 也带电量，但可能错报 `0`，所以不采用。任何来源的电量为 `0` 都不覆盖已有的有效值，也不触发低电报警。

### 报警包 `AP10` 的类型

| 代码 | 含义 | 处理 |
| --- | --- | --- |
| `01` | SOS | 计入大屏"SOS 告警" |
| `05` `06` | 跌倒 | 计入大屏"跌倒告警" |
| `02` `03` `04` `08` `13` `14` `15` `20` | 低电、脱落、佩戴提醒、房颤、拆卸、红外 | 记为设备事件，不计入六类告警，在大屏"设备事件"里展示（`05` 第四节）；房颤归哪一类见 `00` 第 18 项 |
| `00` | 无报警 | 忽略 |

## 二、连接与会话

```text
手表 ──TCP──▶ Netty（9001）: ① 按 # 切包  ② 解码
                  ▼
        会话：连接 ⇄ IMEI；卡编码按包查绑定，③ 校验数据是否有效
                  ▼
        有界线程池 ──▶ Redis 缓冲
```

- **切包**：TCP 是字节流，一次可能收到半个包或多个包。按 `#` 切开，不完整的留到下次拼接。单包超过 8 KB 丢弃并断开连接。例外是 `AP07`：它带二进制音频，里面可能出现 `#`，所以识别到 `IWAP07` 时按它的长度字段整段读完再丢弃。
- **会话**：登录后只记"连接 → IMEI"。没登录就发其他包的连接，数据丢弃并关闭连接；连上 30 秒内不发 `AP00` 也关闭。同一 IMEI 再次登录，新连接替换旧连接。10 分钟没有任何数据的连接主动关闭。
- **卡编码**：不存在会话里。每个包处理时，从"IMEI → 卡编码"绑定缓存里查，收到时就把当时的卡编码写进这条数据，之后不再改。缓存每 60 秒从 `DEVICE` 表刷新一次，后台修改绑定时立即刷新。这样手表换绑后，新数据马上记到新的人名下，不用等手表重连。
- **资源上限**：最多同时 `WATCH_MAX_CONNECTIONS` 个连接（默认 2000），超过的新连接直接关闭。
- **认证**：协议本身没有认证，任何能连上 9001 的设备都能用任意 IMEI 登录，挤掉真的手表。部署时用防火墙只放行手表所在网段（`08` 阶段 7）。
- **设备登记**：

| 手表 | 体征、心跳 | `AP10` 的 SOS、跌倒 |
| --- | --- | --- |
| 已登记、已绑定 | 正常入库 | 生成事件，带卡编码 |
| 已登记、未绑定 | 体征不入库（体征表以卡编码为准），只计数；心跳照常更新设备的在线时间和电量 | 照常生成事件，卡编码为空、记设备号，大屏上可见（见 `05`） |
| 未登记 | 回复登录（免得手表反复重连），数据不入库，只计数、限频记日志 | 同上 |

- **线程**：Netty 线程只收发和切包，不做数据库操作。后续处理交给有界线程池（线程名前缀 `watch-data-`，队列满时由提交者自己执行，起回压作用）。

## 三、数据有效性

手表没戴好时仍会上传，值是 `0` 或占位值：

| 情况 | 处理 |
| --- | --- |
| 心率、血压、血氧、体温为 `0` 或空 | 丢弃该指标 |
| `APHP` 中出现 `0,0,0,95,0.0,0.0`（血氧 `95` 是未佩戴占位值） | 整个包丢弃 |
| 超出合理范围 | 丢弃 |

合理范围只用来筛掉明显错误，不是预警阈值：心率 30–220、血氧 50–100、体温 30.0–45.0、收缩压 60–260、舒张压 30–160、电量 1–100。被丢弃的数据按原因累计到指标 `health.watch.dropped`，页面不展示。

## 四、预警

数据通过有效性检查后立刻判断，不等写库。事件量小，又要尽快出现在大屏上，所以直接写 `ALERT_EVENT`，不走缓冲。

| 类型 | 来源 | 例子 |
| --- | --- | --- |
| 体征越界 `THRESHOLD` | 服务器按阈值判断 | 心率过高、血氧过低 |
| 设备报警 `DEVICE` | 手表 `AP10` 主动上报 | SOS、跌倒 |

SOS 只来自 `AP10` 的 `01`。

**阈值按岗位类别分**：干重活的人心率本来就高，所以不同岗位用不同的正常范围。做法是把厂家的工种归成几个**岗位类别**（如采掘、机电、运输、通风安全、管理），每个类别一套阈值：

1. 由卡编码查到这个人的工种（`POS_PERSON.JOB_KIND`）；
2. 由工种查到岗位类别（`JOB_KIND_GROUP`）；工种没归类、工种为空、手表未绑定，都用默认类别 `DEFAULT`；
3. 取这个类别该指标的阈值（`ALERT_RULE`）；这个类别没配这一项，就用 `DEFAULT` 的。

判断时用到的岗位类别记进事件（`ALERT_EVENT.RULE_GROUP`），事后能查到当时按哪套标准判的。人员工种和归类表跟阈值一起每分钟刷新进内存。

**阈值**存 `ALERT_RULE`，不写死在代码里，上线后随时可以改：启动时读入内存，之后每分钟重新读一次，改完最多 1 分钟生效。阶段 8 的后台提供修改页面，在那之前用 SQL 直接改表。通过后台修改时写操作日志（`ALERT_RULE_SET`，记改前改后的值）；直接改表不会留日志，所以后台做好后只通过后台改。

下面是建表时写入的 `DEFAULT` 类别初始值，目前是开发占位值。上线前请矿上医务人员定下岗位类别、各类别的阈值（`00` 第 3、22 项）：

| 指标 | 偏低 | 偏高 |
| --- | --- | --- |
| 心率（次/分） | < 50 | > 120 |
| 血氧（%） | < 90 | — |
| 体温（℃） | < 35.0 | > 37.3 |
| 收缩压（mmHg） | < 90 | > 140 |
| 舒张压（mmHg） | < 60 | > 90 |

**去重**：同一个人（没绑定时按设备号）、同一事件代码，距**上次发生**（`LAST_OCCURRED_AT`）不到去重间隔，就不新建事件，只更新最近发生时间和次数。所以一段持续的异常只算一条事件，而不是每分钟一条。

- 间隔：体征越界 30 分钟；SOS 和跌倒 2 分钟（重复包多半是同一次事件）。可配置，见 `01` 配置表。
- **事件不跨天**：过了 0 点再发生，算新的一条。这样"今天""本月"的事件数口径清楚。
- 去重以 `ALERT_EVENT` 表为准：启动时把当天仍在间隔内的事件读进内存。同一个人的判断和写入按卡编码（或设备号）加锁串行，避免两个线程同时新建。

## 五、存储

约 200 块表、每块每分钟 1 条，一天约 30 万条，一条条写库会拖慢系统，所以先放 Redis 再成批写。

每条指标数据在收到时就带上：唯一编号 `MSG_ID`（进程内生成，毫秒时间戳 × 1000 + 序号）、IMEI、卡编码、采集时间。

```text
有效数据 ──▶ hv2:watch:buf ──(每 5 秒，Lua 脚本原子地移走最多 1000 条)──▶ hv2:watch:processing
                                                                        │ 一个数据库事务：
                                                                        ├─ 插入 HEALTH_RECORD（MSG_ID 已存在的跳过）
                                                                        ├─ 更新 HEALTH_LATEST（只接受更新的时间）
                                                                        ├─ 更新 STEP_DAILY（覆盖为最新累计，见下）
                                                                        ├─ 更新 DEVICE 的最后在线时间和电量（只接受更新的时间）
                                                                        └─ METRIC_COUNTER 加上本批实际新插入的条数
                                                                        ▼
                                                            提交成功后，从 processing 删除这一批
```

"原子地"指"移出 buf"和"放进 processing"一步完成，中间崩溃也不会两边都没有。

每一步写入都是"重复做一遍结果不变"的：流水按 `MSG_ID` 去重，最新值、步数、在线时间只接受更新的时间，计数只加真正新插入的条数。所以同一批数据被处理两次，既不会重复入库，也不会重复计数。

| Redis key | 类型 | 用途 |
| --- | --- | --- |
| `hv2:watch:buf` | 列表 | 待写库的数据 |
| `hv2:watch:processing` | 列表 | 正在写库的一批，提交成功后删除 |
| `hv2:watch:dead` | 列表 | 写不进库的单条数据，人工排查 |
| `hv2:watch:step:<imei>` | 哈希 | 步数计算状态（见下） |

- **写库失败**：整个事务回滚，这一批留在 `processing`。下一轮先重试它：把这一批对半拆开分别写，还失败的继续拆，直到找出写不进去的单条。单条重试 3 次仍失败，移进 `dead` 并记告警日志，其余数据照常入库。
- **进程崩溃或重启**：启动时先处理 `processing` 里留下的批次，再处理 `buf`。
- **Redis 不可用**：降级为进程内的有界内存队列（上限 10000 条），照常批量写库；队列满了丢弃最旧的并计数。进程崩溃时，内存队列里的数据会丢，这是降级期间接受的代价。Redis 恢复后，先写完内存队列，再切回 Redis。
- **最新值**不放 Redis，放在 Oracle 的 `HEALTH_LATEST`（每人每指标一行），大屏直接查它，Redis 重启不受影响。

**在线** = `DEVICE.LAST_SEEN_AT` 在在线窗口内（默认 20 分钟，见 `01` 配置表）。每个上行包（心跳、体征、报警、指令确认都算）都在内存里刷新这块表的最后上行时间，每批写库时一起写进 `DEVICE`。手表每项体征约每 4 分钟才测一次（见下节），窗口要明显长于测量周期。

**步数**：`AP03` 里的步数是手表上的累计计数器，**不按天归零**，到上限后从 0 重新计（协议示例是 9999，也可能是 65535）。今天的步数 = 今天各次读数的增量之和。

增量在**收到心跳时**就算好，不在写库时算，免得重试、乱序打乱先后。每块表在 `hv2:watch:step:<imei>` 里存：上次读数、上次读数时间、卡编码、日期、今天累计，用 Lua 脚本原子更新：

| 情况 | 增量 |
| --- | --- |
| 没有上次读数（新表、首次上线、状态丢失） | 0，只记下这次读数作起点 |
| 卡编码和上次不同（换绑） | 0，重新作起点 |
| 这次读数时间早于上次（乱序） | 忽略这次读数 |
| 新读数 ≥ 上次 | 差值 |
| 新读数 < 上次（计数器回绕或手表重启） | 新读数本身（回绕前的一小段会少算，可接受） |

- **跨天**：0 点后的第一次读数，"今天累计"从 0 开始，但"上次读数"保留，照常算增量。0 点前最后一次读数到这次之间走的步数，算进新的一天。
- 算好的"今天累计"随心跳数据进缓冲，写库时直接**覆盖** `STEP_DAILY`（只接受更晚的读数时间），重复写不会重复累加。
- Redis 不可用时，状态从 `STEP_DAILY` 的 `LAST_RAW`、`UPDATED_AT` 读，结果也只写 `STEP_DAILY`。

## 六、服务器下发测量指令

手表不会自己按需测量。

登录成功后：

1. 下发 `BP33`，工作模式设为正常（1）。
2. 下发 `BP86`、`BP87`，关闭手表自己的测量周期，避免两套调度重叠。
3. 每 60 秒给每块表下发一项测量，按顺序轮换，不同时启动多个传感器：`BPXL`（心率）→ `BPXY`（血压）→ `BPXZ`（血氧）→ `BPXT`（体温）→ 回到心率。每项指标约每 4 分钟测一次；节奏由 `WATCH_MONITORING_REFRESH_SECONDS` 配置（默认 60），周期同比例变化。

```text
服务器发：IWBPXL,353456789012345,080835#    (IMEI，指令流水号)
手表回：  IWAPXL,080835#                     (只是确认收到，服务器不回复)
随后手表发：IWAP49,68#                        (这才是真实心率)
```

## 七、手表模拟器（`tools/watch-simulator/`）

Python（`asyncio`），模拟 N 块手表（默认 200），一次只能启动一个实例：

- 每块表一个 IMEI，连接 `127.0.0.1:9001`，先发 `AP00` 登录；收到测量指令就回确认，再发对应数据包；定时发 `AP03`（电量缓慢下降，步数累加并在上限处回绕）。
- 数值符合真实分布，并能制造场景：高心率、低血氧、SOS、跌倒、没戴（发 `0`）、掉线重连、未绑定手表发 SOS。
- 手表与人的绑定读一份配置（IMEI ↔ 卡编码），和定位文件生成器用同一批假人。

## 八、指标

通过 Spring Actuator 暴露，名称以 `health.` 开头：

- `health.watch.connections`：当前连接数。
- `health.watch.online.count`：在线手表数，口径同上面的"在线"。
- `health.watch.packets`：收包数，按协议号。
- `health.watch.dropped`：丢弃数，按原因。
- `health.buffer.size`：缓冲积压。
- `health.buffer.flush.duration`：每批写库耗时。
- `health.buffer.split` / `health.buffer.dead`：拆批次数、进死信条数。
- `health.buffer.memory.dropped`：降级队列满时丢弃的条数。
- `health.alert.created`：新预警数，按类型。
