# 02 定位文件解析器

依据：国家煤监局《煤安监办〔2019〕42号 附件2》第 6 章，以及 5 个厂家真实样例（`reference/vendor-samples/`）。

## 一、文件类型

| 类型 | 内容 | 处理 |
| --- | --- | --- |
| `RYQY` | 区域（如"-750大巷"） | 解析入库 |
| `RYJZ` | 基站（编码、名称） | 解析入库，只取名称，忽略坐标 |
| `RYXX` | 人员（卡编码、姓名、工种、职务、部门） | 解析入库，忽略出生年月和学历 |
| `RYSS` | 人员实时位置和出入井 | 解析入库（最核心） |
| `JZSS` | 基站运行状态 | 解析入库 |
| `RYCS` `RYCY` `RYYJCS` | 超时 / 超员 / 厂家自加 | 直接删除，不备份 |
| 其他 | 包括协议里的 `RYXZ`（进入限制区域）、`RYQJ`（人员求救） | 不解析，移到备份目录，记录"未识别的文件类型"（`RYQJ` 是否展示见 `00` 第 17 项） |

除上面三种外，收到的文件一律不删除。

## 二、目录与流程

```text
runtime/
├── inbox/jxry/<煤矿编码>/                收件箱（以后是 FTP 的落地目录）
├── backup/jxry/<煤矿编码>/<yyyyMMdd>/    备份：永不自动删除
└── error/jxry/<煤矿编码>/                解析失败的原文件
```

后端每 30 秒扫描收件箱，对每个文件依次：

```text
1. 文件名合法、是普通文件？  否 ──▶ 移到 error
2. 属于直接删除的类型？      是 ──▶ 删除，记一行日志，结束
3. 文件完整？              末尾没有 || ──▶ 本轮跳过
4. 处理过？                文件名+摘要都相同 ──▶ 记一行 DUPLICATE，移到备份，结束
5. 解析并写库              一个事务
6. 成功 ──▶ 移到备份       失败 ──▶ 回滚，移到 error
```

**第 1 步**：文件名格式 `<煤矿编码12位>_<类型>_<上传时间14位>.txt`，如 `620823009203_RYSS_20260923101319.txt`，正则 `^(\d{12})_([A-Z]+)_(\d{14})\.txt$`。另外三条：

- 煤矿编码必须等于配置里的本矿编码（`POSITIONING_MINE_CODE`），别的矿的文件移到 `error/`；
- 只处理普通文件，符号链接（指向别处的"快捷方式"）移到 `error/`，不跟着读；
- 所在子目录 `jxry/<煤矿编码>/` 要和文件名里的煤矿编码一致。直接放在 `inbox/` 或 `inbox/jxry/` 下的文件也移到 `error/`，处理记录里写明"应放在 `jxry/<煤矿编码>/` 下"；
- 以 `.` 开头的隐藏文件（如 macOS 的 `.DS_Store`、上传工具的临时文件）不处理，也不移动。

移到 `error/` 的文件放在它原来所在的子目录下（如 `error/jxry/610000000001/`），不在任何子目录里的放在 `error/` 根目录；都记一行 `FAILED`。这类文件不读内容，`SHA256` 为空。

**第 3 步**：协议规定文件以 `||` 结尾。去掉末尾空白后，最后两个字符是 `||` 才算完整。不完整说明还在放入或传输，本轮跳过（不解析、不移动、不报错）；文件最后修改时间距现在超过 10 分钟仍不完整，才移到 `error/`。按修改时间算，后端重启也不会重新计时。

**第 4 步**：`POS_INGEST_FILE` 记录每个处理过的文件的文件名和 SHA-256。同名同摘要、且之前那份已入库（`DONE`、`PARTIAL`、`STALE`）视为重复，不再入库；之前那份是 `FAILED` 的不算重复，修好后可以重新放进来。重复的文件但仍记一行 `DUPLICATE` 并移到备份，避免收件箱积压。备份目录里已有同名文件时，新文件名后加 `.dup1`、`.dup2`…，不覆盖原来的。

**第 5 步**：一个文件一个事务。单条记录有问题不应让整个文件失败：

| 情况 | 处理 |
| --- | --- |
| 文件头不合法（少于 3 段、时间格式错、煤矿编码与文件名不符） | 整个文件失败，移到 `error/` |
| 文件头时间比服务器现在晚超过 5 分钟（`POSITIONING_FUTURE_TOLERANCE_MINUTES`） | 整个文件失败，移到 `error/`，写错误日志。否则一份时间错到未来的文件会一直被当成"最新"，之后所有正常文件都不再生效 |
| 记录数为 0 | 正常（空快照） |
| 记录字段数不对，或关键字段为空 | 跳过该记录，记入 `POS_INGEST_ERROR`，文件标记"部分成功" |
| 超过 20% 的记录出错 | 整个文件回滚，移到 `error/`（格式可能整体变了） |
| 文件大于 20 MB | 不解析，移到 `error/`（样例最大的 `RYXX` 才 120 KB） |
| 不是 UTF-8 编码 | 整个文件失败，移到 `error/` |

"关键字段"和字段检查：

| 字段 | 规则 |
| --- | --- |
| 人员卡编码、基站编码（`RYJZ`、`JZSS`）、区域编码（`RYQY`） | 必填，分别是 17、22、16 位数字 |
| `RYSS` 的出入井标志 | 必填，`0`、`1`、`2` 之一 |
| `RYSS` 里的区域编码、基站编码 | 可空；有值时位数同上 |
| 时间 | 可空；有值时必须是 `yyyy-MM-dd HH:mm:ss` |
| 是否矿领导、是否特种人员 | 可空；有值时必须是 `0` 或 `1` |
| 基站运行状态、供电状态 | 可空；有值时必须是 `0`、`1`、`2`、`9` |
| 核定人数、距离基站距离 | 可空；有值时必须是数字 |
| 姓名、名称等文字 | 可空；超过表里的列长度算出错（不截断） |

**第 6 步**：顺序是"先复制到备份目录 → 写库并提交 → 删除收件箱里的原文件"：

- 复制失败（磁盘满、没权限）：不写库，原文件留在收件箱，下一轮重试；
- 写库失败：删掉备份里的那份，原文件移到 `error/`，记一行 `FAILED`；
- 数据库连不上（连接失败、超时这类暂时性的错误）：不算文件的错，原文件留在收件箱，本轮剩下的文件也不再处理，下一轮重试；
- 提交后删原文件失败：数据已入库、已备份；下一轮这份文件会被当成重复文件移走。

备份子目录 `<yyyyMMdd>` 取文件名里上传时间的日期。`POS_INGEST_FILE.BACKUP_PATH` 记文件的去处，如 `backup/jxry/620823009203/20260923/xxx.txt` 或 `error/jxry/620823009203/xxx.txt`。

同一轮里先处理文件名上传时间早的，减少不必要的 `STALE`。

## 三、文件格式

共同规则：

- UTF-8，无 BOM；时间格式 `yyyy-MM-dd HH:mm:ss`。
- 没有换行符：`~` 结束一条记录，`||` 结束整个文件。第一段是文件头，之后每段一条记录。
- 字段用英文分号 `;` 分隔，**空字段也保留分号**，拆分时要保留空字段（Java 用 `split(";", -1)`）。
- 去掉每段前后的空白和混进来的 `\r` `\n`。遇到全角分号 `；` 视为格式错误，记入错误表，不自动修正。

**文件头**：除 `RYXX` 外都是 3 段：`煤矿编码;矿井名称;数据上传时间`。`RYXX` 有 8 段：`煤矿编码;矿井名称;核定下井人数;系统型号;系统名称;厂家名称;安标有效期;数据上传时间`，上传时间在最后一段。

**RYSS（15 段）**

| 序号 | 字段 | 说明 |
| --- | --- | --- |
| 0 | 人员卡编码 | 17 位，人员唯一 ID |
| 1 | 姓名 | |
| 2 | 出入井标志 | `0` 在井口、`1` 已入井、`2` 已出井 |
| 3 | 入井时刻 | |
| 4 | 出井时刻 | 标志为 2 时才有值 |
| 5 | 区域编码 | 16 位 |
| 6 | 进入当前区域时刻 | |
| 7 | 基站编码 | 22 位，前 16 位就是区域编码 |
| 8 | 进入当前基站时刻 | |
| 9 | 劳动组织方式 | 如"三八制" |
| 10 | 距离基站距离 | 米，有正负；仅参考，暂不使用 |
| 11 | 人员工作状态 | `正常` / `求救` |
| 12 | 是否矿领导 | `1` 是 |
| 13 | 是否特种人员 | `1` 是 |
| 14 | 行进轨迹 | 暂不使用，不入库 |

**RYXX（9 段）**

| 序号 | 字段 | 说明 |
| --- | --- | --- |
| 0 | 人员卡编码 | |
| 1 | 姓名 | |
| 2 | 工种 | "未设置"存为空 |
| 3 | 职务 | "未设置"存为空 |
| 4 | 队组/部门 | 原样使用，不清洗（样例里有"来宾""离矿人员"等） |
| 5 | 出生年月 | 忽略（厂家全填 `1990-01-01` 占位） |
| 6 | 学历 | 忽略（全空） |
| 7 | 是否矿领导 | |
| 8 | 是否特种人员 | |

**RYJZ（6 段）**：0 基站编码（22 位）、1 基站名称、2–4 X/Y/Z 坐标（忽略，全是 0 或占位值）、5 位置注释（不入库）。

**RYQY（4 段）**：0 区域类型（原值是 `井口区域` / `重点区域` / `限制区域` / `其它区域` 之一，原样存）、1 区域编码（16 位）、2 核定人数、3 区域名称。

**JZSS（4 段）**：0 基站编码、1 运行状态（`0` 通讯正常、`1` 通讯中断、`2` 故障、`9` 未知）、2 供电状态（`0` 直流、`1` 交流、`2` 电源故障、`9` 未知）、3 数据时间。

## 四、写入哪些表

表结构见 `04`。

| 文件 | 写入表 | 写法 |
| --- | --- | --- |
| `RYQY` | `POS_AREA` | 按区域编码 `MERGE`（有则更新，无则插入） |
| `RYJZ` | `POS_STATION` | 按基站编码 `MERGE`，只更新名称 |
| `JZSS` | `POS_STATION` | 按基站编码 `MERGE`，更新运行/供电状态；基站不存在就先插入，名称留空 |
| `RYXX` | `POS_PERSON` | 按卡编码 `MERGE`，更新厂家字段，不碰人工录入的年龄（唯一的例外：卡编码换了姓名，见下面"卡编码换了姓名"） |
| `RYSS` | `POS_PERSON_STATE` | 按卡编码 `MERGE`，更新位置和出入井状态 |
| `RYSS` | `POS_PERSON` | 卡编码不在人员表里就补一行（只有卡编码、姓名）；已有的人不改姓名 |
| `RYSS` | `POS_PRESENCE_DAILY` | 按（快照日期，卡编码）`MERGE`，记录最早入井、最晚出井时刻（日期怎么算见 `04`） |
| `RYSS` | `POS_HEADCOUNT_SERIES` | 每份文件按时刻 `MERGE` 一行：这个时刻井下多少人 |
| 全部 | `POS_INGEST_FILE` | 每个文件一行处理记录 |

### 以时间最新为准

比较的是文件头里的"数据上传时间"，不看到达先后。

- **逐行比较**：每张表记着这行数据依据的文件时间（`SRC_DATA_TIME`），`MERGE` 只在新文件时间 ≥ 库里这一行的时间时才更新。所以旧文件后到，只会补上库里比它还旧的行，不会覆盖新数据。
- **历史类的表照常写**：`POS_PRESENCE_DAILY`（取最早入井、最晚出井）和 `POS_HEADCOUNT_SERIES`（每个时刻一个点）与到达先后无关，旧文件照常写入，补全曲线。
- **文件状态**：文件头时间早于同类型已生效的最新文件时，状态记 `STALE`（过期）。`STALE` 文件不会成为 `V_POS_IN_WELL` 的"最新快照"。

同一个文件里同一编码（人员卡编码、基站编码、区域编码）出现多次，以靠后的一条为准，在 `POS_INGEST_ERROR` 记一条 `KIND = 'WARN'` 的警告（不算出错，文件仍是 `DONE`）。样例 `RYXX` 里有 1 个卡编码出现两次，两条的姓名、部门都不同。卡和人不一一对应的处理见下面"卡编码换了姓名"。

**卡编码换了姓名**（`00` 第 21 项，已定）：卡编码就代表人，以最新文件为准。`RYXX` 入库时，如果一条要生效的记录（条件和上面的 `MERGE` 一样：库里这个人是 `RYSS` 补录的，或者文件时间不早于库里的）姓名和库里不同，说明这张卡可能给了别人：

- 照常更新姓名、部门、工种等厂家字段；
- 清空人工录入的年龄（`AGE`、`AGE_UPDATED_BY`、`AGE_UPDATED_AT`），并写一条操作日志 `PERSON_AGE_SET`：操作人是系统（登录名 `SYSTEM`、账号 ID 为空），改动前 `{ "age": 45 }`，改动后 `{ "age": null, "reason": "定位文件里这个卡编码换了姓名" }`；没录过年龄的不写日志；
- 在 `POS_INGEST_ERROR` 记一条 `KIND = 'WARN'`，行号是这条记录在文件里的位置，原因写"卡编码换了姓名（原：张三），已清空人工录入的年龄 45，请人工核对手表绑定和名单"（含姓名，只在库里，页面不展示），后端日志另写一行（只写卡编码，不写姓名）；文件状态仍是 `DONE`；
- 手表绑定、重点监护/今日关注名单不动，由人核对后处理（后台管理里的换卡记录、警告列表在阶段 8 做）。

只看 `RYXX`：只有它会改姓名；`RYSS` 对已有的人不改姓名，所以不触发。旧文件后到不覆盖新姓名，也不算换名。同一个文件里卡编码重复的，先按上一段取靠后的一条，再和库里比。

**人员表的例外**：从 `RYSS` 补录的人（`FROM_RYXX = 0`）只有卡编码和姓名。`RYXX` 不论新旧都可以补全他，补全后 `FROM_RYXX = 1`，之后再按文件时间判断新旧。否则厂家样例这种情况会出错：`RYXX` 是 3 月的、`RYSS` 是 9 月的，先到的 `RYSS` 补录的人，再也等不到部门和工种。

**每日出入井**（`POS_PRESENCE_DAILY`）：

- 快照里出入井标志为 `1` 的人：在快照日期那天 `MERGE` 一行，`FIRST_IN_TIME` 取较早的入井时刻，`LAST_SEEN_TIME` 取较晚的快照时间；
- 标志为 `2` 的人：出井时刻写到这趟下井涉及的每一天（从入井日期到快照日期），取较晚的；那天没有行就不写。所以跨零点的夜班，两天的行都有同一个出井时刻；
- 标志为 `0`（在井口）的不写。

### `RYSS` 是全量快照

协议说 `RYSS` 的文件体是"煤矿下所有井下作业人员实时数据的集合"，所以每份 `RYSS` 看作一张完整快照：井下人数 = **最新一份** `RYSS` 里出入井标志为 `1` 的人数；不在最新快照里的人视为不在井下（他们在 `POS_PERSON_STATE` 里的记录保留，数据时间较旧）。

样例里既有在井（82 人）又有已出井（3 人），说明快照带着刚出井的人；是否含"当班所有人"待确认（`00` 第 15 项），当前做法对两种情况都成立。

### 数据过期

厂家每 5 分钟发一份 `RYSS`。最新一份的上传时间距现在超过过期阈值（见 `01` 配置表），页面显示"定位数据已过期"和最后数据时间。

## 五、失败处理

| 问题 | 处理 |
| --- | --- |
| 解析失败 | 文件进 `error/`，`POS_INGEST_FILE.STATUS='FAILED'`，`ERROR_MSG` 写原因 |
| 长时间没有新文件 | 页面提示数据过期；`GET /api/positioning/status` 返回最后一份文件的时间 |
| 备份目录写不进（磁盘满、权限） | 文件留在收件箱，不入库，下一轮重试，写错误日志 |

备份不自动清理。样例估算：`RYSS` 每 5 分钟 68 KB，一天约 20 MB，一年约 7 GB；`JZSS` 协议规定每 1 分钟一份，约 6 KB，一年约 3 GB。合计一年约 10 GB，部署时留够磁盘。

## 六、模拟器与测试

**定位文件生成器**（`tools/positioning-sim/sim.py`，只用 Python 标准库）按协议格式造文件放进收件箱，和真实数据走同一条路：

- 一套一致的假数据：假人（假姓名，卡编码格式与真实一致）、区域、基站。卡编码要和手表模拟器绑定的一致，这样"在井下 + 手表在线"才能联动。
- 定时生成 `RYSS`：人在基站间移动，有入井、有出井。
- 能故意造异常：半个文件、字段数不对、旧文件后到、重复文件、`RYCS`、未知类型。

假数据固定一套（同一个随机种子，每次生成都一样）：12 个区域、38 个基站、120 个假人。假人卡编码是 `<煤矿编码>9xxxx`（`90001` 起），厂家真实卡编码是 `0`、`1` 开头，不会撞上。三八制三个班，每人每天入井、出井时间错开几十分钟，所以平时井下三十多人，交接班时五十多人，不会突然变成 0。谁在井下、在哪个基站存在 `runtime/positioning-sim/state.json`。

用法（在 `health-v2/` 下运行）：

| 命令 | 作用 |
| --- | --- |
| `python3 tools/positioning-sim/sim.py base` | 生成 `RYQY`、`RYJZ`、`RYXX` |
| `python3 tools/positioning-sim/sim.py tick` | 推进一步，生成一份 `RYSS` 和 `JZSS` |
| `python3 tools/positioning-sim/sim.py run` | 先 `base`，再每 5 分钟 `tick` 一次（`--interval 秒数` 改间隔） |
| `python3 tools/positioning-sim/sim.py bad <类型>` | 造异常文件：`half` 半个文件、`fields` 一条字段数不对、`ratio` 一半记录出错、`old` 旧文件后到、`future` 时间在未来、`dup` 重复文件、`rycs`、`unknown`（`RYQJ`）、`other-mine` 别的矿 |
| `python3 tools/positioning-sim/sim.py people --json` | 输出假人名单，阶段 2 绑定手表用 |
| `python3 tools/positioning-sim/sim.py reset` | 清空模拟状态 |
| `python3 tools/positioning-sim/sim.py --inbox <测试收件箱> backfill --from 2026-09-01 --to 2026-10-01` | 按过去的时间补一段 `RYSS`（默认每小时一份），给月报测试用（`08` 阶段 6 的历史数据回填）。从"谁都不在井下"开始推进，不读写 `state.json`；必须用 `--inbox` 指定测试后端的收件箱，拒绝业务收件箱 `runtime/inbox`。旧文件后到记 `STALE`，但每日出入井照常写入 |

文件先写到 `runtime/positioning-sim/tmp/`，写完再改名放进收件箱，后端不会读到写了一半的文件。收件箱里已有同名文件时，文件名里的时间往后推 1 秒，不覆盖还没处理的文件。

**测试**只用脱敏的假数据，真实样例（含真实姓名）不入库。解析器的单元测试（`PositioningParserTest`）不连数据库；下面的必测用例在 `PositioningInboxTest` 里，用真实的临时目录和 Oracle 测试用户端到端地跑（测试用户见 `01` 配置表）。必测：

| 用例 | 期望 |
| --- | --- |
| 正常 `RYSS` | 入库条数正确 |
| 末尾缺少结束符（两个竖线） | 跳过，不入库，不移动 |
| 空字段 | 位置保留，字段不错位 |
| `RYXX` 文件头 | 上传时间取第 8 段 |
| 同一卡编码换了姓名（`RYXX`） | 姓名以新文件为准，人工录入的年龄被清空并有 `SYSTEM` 的操作日志，`POS_INGEST_ERROR` 有一条带行号的 `WARN`，文件仍是 `DONE`；姓名没变的人年龄不动；旧文件后到不改回旧姓名 |
| 同一文件放两次 | 只入库一次，两份都备份（第二份文件名带 `.dup1`），处理记录有一行 `DUPLICATE` |
| 旧文件后到 | 不覆盖新数据，状态 `STALE`，井下人数不变 |
| 文件头时间在未来 | 移到 `error/`，井下人数不变 |
| 20% 以上记录错误 | 整个文件回滚 |
| `RYCS` | 被删除，没有备份 |
| 符号链接 | 移到 `error/`，不读取它指向的文件 |
| 别的矿的煤矿编码 | 移到 `error/` |
