# 05 页面与接口

**所有数字由后端算好，前端只负责显示。** 页面的布局位置和样式见 `09`，本文里的示意图只表示大致结构。

## 一、页面

前端用 hash 路由，如 `/#/dashboard`。

| 路由 | 页面 |
| --- | --- |
| `/login` | 登录页（沿用老项目的登录页，复制后独立使用）。`LOGIN_SHOW_DEFAULT_ACCOUNT` 为 `true` 时，登录框下方明文提示"默认账号 admin，密码 admin"，提示内容由后端 `GET /api/auth/login-hint` 返回（不需要登录），为 `false` 时返回空、页面不显示 |
| `/portal` | 入口页，登录后默认进入 |
| `/dashboard` | 动态数据（大屏）：展示模式（默认）、地图模式（`?mode=map`） |
| `/archive` | 健康档案（人员卡片列表） |
| `/archive/:cardCode` | 个人档案 |
| 弹层 | 月度汇总（翻书）、佩戴情况（确认后下载 Excel） |

顶部导航：动态数据 · 健康档案 · 账号菜单（退出登录；"数据管理"暂未开放，点击提示"建设中"）。

## 二、通用规则

**面板状态**：每个面板要处理四种状态。

| 状态 | 表现 |
| --- | --- |
| 加载中 | 骨架屏，不闪 `0` |
| 没有数据 | 显示"暂无数据" |
| 未录入 | 显示"未录入"（如没有年龄） |
| 刷新失败 | 保留上次数据，面板角落写"刷新失败，显示的是 hh:mm 的数据" |

后端拿不到的数据返回 `null`，前端据此显示"暂无数据"或"未录入"，不显示 `0`。

**数据新鲜度**：定位数据超过过期阈值（见 `01` 配置表）没更新，页面顶部显示黄色横幅"定位数据已过期，最后更新 hh:mm"（不是今天的写成"MM-dd hh:mm"；从没收到过定位数据写"还没有收到定位数据"），页面角落常驻显示定位数据时间和手表数据时间。定位数据过期时，人数仍按最后一份 `RYSS` 显示，靠横幅提醒。

- 定位数据时间：最新一份生效的 `RYSS` 的数据上传时间（各接口的 `positioning.dataTime`）。
- 手表数据时间：库里最新一条体征的采集时间（`HEALTH_LATEST` 的最大 `COLLECTED_AT`，`dashboard/overview` 的 `dataTime`）。
- 入口页角落另写"体征统计"时间：今天日汇总最近一次重算的时间（`portal/summary` 的 `dataTime`），因为入口页的体征数字来自日汇总，最多晚 5 分钟。

**刷新失败**：某一轮刷新有接口失败时，页面顶部再显示红色横幅"刷新失败，显示的是 hh:mm 的数据"；失败的面板标题栏写"刷新失败 · hh:mm"（右侧面板窄，放不下整句；悬停看整句）。hh:mm 是这个面板上次刷新成功的浏览器时间。下一轮成功后自动消失。横幅放在页头标题和导航之间的空处（`09` 第二节）。

**刷新**：入口页、动态数据和地图模式每 30 秒（手动刷新与自动刷新共用一个倒计时，不并发重复请求：一轮全部返回后才开始下一轮的倒计时）；个人档案 60 秒；健康档案列表不自动刷新。

**人员编号**：卡编码 17 位，页面表格和卡片显示"卡号"（后 5 位），悬停显示完整 17 位；Excel 导出和接口用完整 17 位。

**接口**：路径以 `/api` 开头；除登录外都要登录，令牌放请求头 `satoken`；返回格式和分页见 `01`；带数据时间的接口返回 `dataTime`（数据自己的时间）。时间一律写成北京时间 `"2026-09-24 10:13:19"`，日期写成 `"2026-09-24"`（`common/config/JacksonConfig`）。

## 三、入口页

```text
┌──────────────────────────────────────────────────┐
│  心率监测            [中间大圆环]        血氧监测   │
│  最大 最小 平均      预渲染动画          最大 最小 平均 │
│  [数据管理]                              [数据展示] │
│  体温监测                                运动步数   │
│  最大 最小 平均                          最大 最小 平均 │
│   ○重点监护  ○当日关注   ○职工数量   ○监护设备数量   │
└──────────────────────────────────────────────────┘
```

| 内容 | 口径 |
| --- | --- |
| 心率/血氧/体温的最大、最小、平均 | 今天 0 点起所有有效读数（`HEALTH_DAILY_SUMMARY` 今天各人的合并，平均按样本数加权，保留 1 位小数）。日汇总每 5 分钟重算一次，所以最多晚 5 分钟；今天还没有汇总时整项为 `null` |
| 运动步数的最大、最小、平均 | 今天每个人步数（`STEP_DAILY`，记录为 0 步的也算）的最大、最小、平均（取整）；今天没有记录时为 `null` |
| 重点监护 / 当日关注 | `WATCH_LIST` 中 `KEY` 的人数 / `TODAY` 且 `EXPIRE_DATE` 不早于今天的人数 |
| 职工数量 | 当前井下人数（`V_POS_IN_WELL`）；从没收到过 `RYSS` 时为 `null` |
| 监护设备数量 | `DEVICE` 中启用（`STATUS = 1`）的手表数，不管绑没绑定 |

`dataTime` 是今天日汇总最近一次重算的时间（没有为 `null`）。

`GET /api/portal/summary`：

```json
{
  "dataTime": "2026-09-24 10:13:19",
  "vitals": {
    "HEART_RATE":  { "max": 180, "min": 41, "avg": 81.1 },
    "SPO2":        { "max": 99,  "min": 84, "avg": 94.7 },
    "TEMPERATURE": { "max": 37.5,"min": 36.2,"avg": 36.6 },
    "STEPS":       { "max": 26523, "min": 1, "avg": 9361 }
  },
  "keyPersonCount": 0, "todayWatchCount": 0,
  "inWellCount": 18, "deviceCount": 200,
  "positioning": { "dataTime": "...", "stale": false }
}
```

### 展示模式

`GET /api/dashboard/overview`：

```json
{
  "dataTime": "2026-09-24 10:13:19",
  "totalCollected": 6471495,
  "collected": { "HEART_RATE": 5219387, "SPO2": 602780, "TEMPERATURE": 649328, "BLOOD_PRESSURE": 0 },
  "alerts": { "SOS": 0, "FALL": 0, "HEART_RATE": 0, "BLOOD_PRESSURE": 0, "SPO2": 0, "TEMPERATURE": 0 },
  "alertWindow": "today",
  "deviceEventCount": 3
}
```

| 内容 | 口径 |
| --- | --- |
| 累计采集数据（大数字） | `METRIC_COUNTER` 各指标累计条数之和 |
| `dataTime` | 手表数据时间：`HEALTH_LATEST` 里最新的 `COLLECTED_AT`；还没有任何体征时为 `null` |
| 心率 / 血氧 / 体温 / 血压（四个平台） | 各自累计条数 |
| 左侧"佩戴情况" | 确认框 → 下载 Excel（见下） |
| 左侧"月度汇总" | 打开翻书报告（`07`） |

### 右侧：六类告警

SOS、跌倒、心率、血压、血氧、体温。口径：`ALERT_EVENT` 里 `LAST_OCCURRED_AT` 在今天 0 点之后、对应 `CATEGORY` 的**人数**（同一个人多条事件算 1 个）。

手表未绑定时，事件没有卡编码，按设备号算 1 个"人"，点开显示"未绑定设备 + IMEI"。这样未绑定的手表发出 SOS 也能在大屏上看到（`03` 第二节）。

一条事件不跨天（`03` 第四节），所以"`LAST_OCCURRED_AT` 在今天"和"`OCCURRED_AT` 在今天"是一回事；后端按后者查，能用上 (`CATEGORY`, `OCCURRED_AT`) 索引。

**点开格子** `GET /api/dashboard/alerts?category=SOS&page=1&size=20`（`category` 只能是六类之一，否则 400）：今天出过这一类告警的人，一人一行，`total` 就是格子里的数字；按最近一次发生时间倒序。

| 列 | 说明 |
| --- | --- |
| 姓名、卡号、部门 | 未绑定的手表写"未绑定设备"和 IMEI，部门写"—" |
| 最近一次 | 这个人今天这一类里最近的一条事件，如"心率偏高（132）"；括号里是那条事件第一次触发时的值，设备报警（SOS、跌倒）不写值 |
| 时间 | 最近一次发生的时间 |
| 今天 | "N 条 / M 次"：事件条数和总发生次数（去重期间的重复也算进次数） |

### 右侧：设备事件

"体征信息展示"面板标题栏右侧有一个"设备事件 N"标记，N 是今天的设备事件条数：`ALERT_EVENT` 里 `SRC = 'DEVICE'`、`CATEGORY = 'OTHER'`、`LAST_OCCURRED_AT` 在今天 0 点之后的事件数（低电、脱落、佩戴提醒、拆卸、红外等；SOS 和跌倒已经在格子里，不重复算）。一段持续的事件只算一条（去重规则见 `03` 第四节）。N 为 0 时标记显示"设备事件 0"，不隐藏。

点标记弹出列表 `GET /api/dashboard/device-events?page=1&size=20`，最新的在前：

| 列 | 说明 |
| --- | --- |
| 姓名、卡号 | 未绑定的手表写"未绑定设备"和 IMEI |
| 事件 | 低电、脱落、佩戴提醒、拆卸、红外…… |
| 时间 | 最近一次发生时间；重复发生的写次数，如"3 次" |

只列今天的（和标记上的 N 一致），每页 10 条翻页。

### 右侧：重点人员

`GET /api/dashboard/key-persons`：重点监护名单里的人，每行姓名、卡号、部门、"详情"（跳转个人档案）。为空显示"暂无重点人员"。按加入时间倒序，不分页（名单是人工维护的，人数少）；部门为空写"未录入"。个人档案在阶段 5 做，之前点"详情"提示"建设中"。

### 底部左：上线职工曲线

`GET /api/dashboard/headcount-series?date=2026-09-24`（`date` 默认今天）：横轴当天 0 点到现在，纵轴井下人数，数据点来自 `POS_HEADCOUNT_SERIES`（每份定位文件一个点）。没有数据的时段不画点、不连线。曲线画井下人数还是已上线人数，见 `00` 第 19 项（目前画井下人数）。

```json
{ "date": "2026-09-24", "gapMinutes": 15,
  "points": [ { "time": "2026-09-24 00:05:00", "inWell": 31 } ] }
```

"没有数据的时段"：相邻两个点隔得比 `gapMinutes`（= 定位过期阈值，`01` 配置表）还久，说明中间没收到文件，曲线在那里断开。纵轴 0 起、每格 3，最少到 18，人多时向上取整到 3 的倍数；横轴刻度按时长取 30 分钟到 3 小时。今天一个点都没有时显示"暂无数据"。

### 底部中：人员信息展示

`GET /api/dashboard/headcount`：

```json
{
  "inWell": 31, "expected": 8, "online": 1, "offline": 7,
  "onlineNormal": 1, "onlineAlert": 0,
  "positioning": { "dataTime": "2026-09-24 10:13:19", "stale": false }
}
```

| 名称 | 口径 |
| --- | --- |
| 井下职工 | `V_POS_IN_WELL` 的人数 |
| 应上线 | 井下职工中绑定了手表的人数 |
| 已上线 | 应上线中手表在线的人数（在线口径见 `03` 第五节） |
| 未上线 | 应上线 − 已上线 |
| 已上线无告警 / 已上线告警 | 已上线中，当前没有 / 有**仍在发生**的六类告警的人数 |

关系：已上线无告警 + 已上线告警 = 已上线。从没收到过 `RYSS` 时六个人数都是 `null`（显示"暂无数据"）；定位过期时仍按最后一份显示。

**仍在发生** = 这个人有六类告警事件的 `LAST_OCCURRED_AT` 在最近 30 分钟内（`ALERT_ACTIVE_MINUTES`，见 `01` 配置表）。体征恢复正常后不再产生新的异常，30 分钟后他自动回到"已上线无告警"。这和上面六个格子不同：格子统计今天一共有多少人出过事，这里只看现在。

**人员表** `GET /api/dashboard/in-well-persons?keyword=&page=1&size=20`：井下的人，手表在线的排前面，其次离线、没绑定；同一状态按姓名。`keyword` 按姓名或卡编码"包含"查（输卡号后 5 位也能查到），按普通文字匹配（`%`、`_` 不是通配符）。每页 20 人，人多时标题栏有翻页。

| 列 | 来源 |
| --- | --- |
| 姓名 | `POS_PERSON.PERSON_NAME` |
| 卡号 | 卡编码后 5 位 |
| 机构 | 部门，没有则"未录入" |
| 区域 | 所在区域名称（`POS_AREA`）；区域表里没有时写"暂无数据" |
| 监测 | 图标：手表在线 / 离线 / 未绑定（`watchState` = `ONLINE` / `OFFLINE` / `UNBOUND`，口径和"已上线"相同：绑定了启用的手表、最后上行在在线窗口内） |

每行另带 `stationPlaced`：他所在的基站在地图上摆放了没有。地图模式下，没摆放的在"区域"下面用小字标"基站未摆放"（展示模式不标）。

点击某一行：切换到地图模式（地址带上 `?mode=map&card=卡编码`）并定位到这个人（第五节）。同一个人再点一次也会重新定位。

### 底部右：实时运动量

`GET /api/dashboard/steps-rank?limit=10`（`limit` 1–50）：今天步数最多的前 N 人（`STEP_DAILY`）。今天有步数记录的人都列出，记录为 0 的显示"0 步"；今天没有记录的人不列。步数相同按姓名排。每人带 `barPct`（进度条长度 = 步数 ÷ 第一名步数 × 100，四舍五入；第一名 0 步时都是 0）。

### 佩戴情况导出

对比"定位系统说在井下的人"和"手表实际上传了数据的人"。点"佩戴情况" → 确认框"此操作将导出下井职工前一天手表佩戴情况" → 下载 Excel。

`GET /api/export/wear?date=2026-09-23`（默认昨天）：

- 文件名 `佩戴情况_yyyyMMddHHmmss.xlsx`（导出时刻），工作表名 `数据上报记录`。文件名在响应头 `Content-Disposition` 的 `filename*`（UTF-8 编码）里，前端按它保存。
- 列：统计日期（`yyyy-MM-dd`）、人员卡编码（完整 17 位，按文本存，免得 Excel 当成数字丢精度）、姓名、部门（没有则"未录入"）、上报数据。
- 名单：`POS_PRESENCE_DAILY` 里那天有入井记录、且**现在**绑定着启用的手表（`DEVICE.STATUS = 1`）的人。"那天"怎么算见 `04` 的 `POS_PRESENCE_DAILY`。绑定关系没有历史记录，所以按导出时的绑定算。按部门、姓名排序。
- 上报数据：那天 0 点到次日 0 点 `HEALTH_RECORD` 有该人记录写"数据上传正常"，否则写"数据未上传"（任意时段都算，`00` 第 20 项）。
- `date` 格式不对、或者晚于今天，返回 400。那天没有人下井时只有表头。

## 五、地图模式

**交互**：

- 左侧入口：重点监护、今日关注（只显示名单里的人，再点一次取消过滤）。过滤时按钮文字变黄，按钮下面写"只显示重点监护名单里的人 · 井下 N 人"（N 是接口返回的人数；新名单的数据回来之前写"读取中……"）。
- 顶部搜索框：输入姓名或卡号回车定位；旁边有刷新按钮。搜索用 `GET /api/map/persons?filter=all&keyword=`（不受名单过滤影响）：一个人直接定位；多个人在搜索框下面列出来（姓名、卡号、区域，基站没摆放的标"基站未摆放"），点一个定位；没有时提示"井下没有找到"xxx""。刷新按钮立即刷新地图的人员、基站和打开的体征卡，和自动刷新共用倒计时（第二节）。
- 点人员图标或列表里的人：地图移到他所在的基站，弹出体征卡。
- 右上角"地图模式"按钮下面是"摆放基站"按钮（`06` 第五节）；左下角圆形按钮显示/隐藏基站。
- 所在基站没摆放的人地图上不画，地图右下角写"N 人所在基站未摆放，地图上没有画"，点开是这些人的名单（姓名、卡号、区域、"基站未摆放"），点一个弹体征卡（停在地图上方，见 `06` 第四节）。
- 人员和基站某一轮刷新失败时，地图左下角写"刷新失败，显示的是 hh:mm 的数据"。

**人员怎么画**：

| 情况 | 表现 |
| --- | --- |
| 所在基站已摆放 | 在该基站位置画人员图标 |
| 多人在同一基站 | 合并成一个图标显示人数，点开展开成列表 |
| 所在基站未摆放 | 地图上不画；列表里显示区域名称，标"基站未摆放" |
| 不在井下 | 不画 |

**体征卡**：

| 内容 | 说明 |
| --- | --- |
| 姓名、卡号、部门 | |
| 位置 | 区域名称 + 基站名称 + 定位时间，写"xx 基站附近" |
| 心率、体温、血氧、血压 | 每项带采集时间，超过"数据较旧"阈值（见 `01` 配置表）没更新的标灰并写"数据较旧" |
| 电量 | 来自心跳，带时间 |
| 手表状态 | 在线 / 离线（最后在线时间）/ 未绑定 |
| 按钮 | "告警记录"（展开最近 3 条）、"档案"（跳个人档案；阶段 5 之前提示"建设中"）；所在基站没摆放时多一个"去摆放" |

告警记录只列六类告警（设备事件不算），按发生时间倒序，每条写最近一次发生的时间、名称和触发时的值（SOS、跌倒不写值）。位置一行写"区域 · 基站附近 + hh:mm 定位"；定位时间是这条位置依据的那份 `RYSS` 的数据上传时间。所在基站"通讯中断"或"故障"时另写一行"所在基站通讯异常，位置可能不准"。人不在井下时位置写"不在井下"。

**接口**：

| 接口 | 用途 |
| --- | --- |
| `GET /api/map/config` | 底图配置：WMS 地址、图层名、坐标系、地图范围 |

`GET /api/map/persons` 每个人（井下的人，按姓名排序，不分页）：

```json
{ "cardCode": "62082300920310025", "name": "…", "dept": "综采一队", "areaName": "下口区域",
  "stationCode": "6208230092030008000012", "stationName": "新副井下口1",
  "placed": true, "x": 39482000.0, "y": 3852000.0,
  "posTime": "2026-09-24 10:13:19", "watchState": "ONLINE", "alerting": false }
```

- `stationName` 是基站的显示名称（`04` `POS_STATION_MARK` 的优先级）；`placed` 为 `false` 时 `x`、`y` 为 `null`。
- `posTime`：这条位置依据的那份 `RYSS` 的数据上传时间。
- `alerting`：有"仍在发生"的六类告警（口径和"已上线-告警"一样，第四节），图标变红。
- `filter` 不是 `all`、`key`、`today` 时返回 400；`keyword` 和人员表一样按姓名或卡编码"包含"查。

## 六、健康档案

## 八、其他接口

**名单**：`GET /api/watch-list?type=KEY`；`POST /api/watch-list`（`{ cardCode, type, note }`）；`DELETE /api/watch-list/{id}`。加入入口在个人档案右上角"加入重点监护 / 今日关注"，再点一次移出。名单只靠人工加入，系统不按告警或其他规则自动加人。"重点监护"一直有效，直到有人移出；"今日关注"当天 24 点自动失效。加入、移除都写操作日志（`WATCH_LIST_ADD` / `WATCH_LIST_REMOVE`）。

**月报**：`GET /api/report/months`、`GET /api/report/monthly?month=2026-08`，见 `07`。

**运维**：`GET /api/positioning/status`（每种定位文件最后一次的处理情况、数据时间、是否过期）；返回 `stale`（最新一份生效的 `RYSS` 距现在超过过期阈值，或从没收到过）、`lastDataTime`（它的数据上传时间）、`inWellCount`（按 `V_POS_IN_WELL` 的井下人数，没收到过 `RYSS` 时为 `null`）、`failedLast24h`（最近 24 小时失败的文件数），以及 `types`：五类文件各一项（已生效的最新数据时间 + 最近处理的一份文件），另有收到过的未识别类型；`GET /actuator/health`（顶层 `status` 为 `UP` 才算可用）；`GET /actuator/metrics`。

**登录**：`GET /api/auth/login-hint`（登录页提示，不需要登录）；`POST /api/auth/login`（`{ username, password }` → `{ token, user }`）；`POST /api/auth/logout`；`GET /api/auth/me`。所有登录用户权限相同。账号在后台管理做出来之前由脚本创建。

**登录锁定**：同一个用户名连续输错 5 次密码，锁定 10 分钟，这期间密码对了也不让登录，提示"密码错误次数过多，请 10 分钟后再试"。失败次数存在 Redis 的 `hv2:auth:fail:<用户名>`：每错一次加 1，第一次出错时设 10 分钟后自动过期（10 分钟内累计不到 5 次，计数自动清零）；第 5 次出错时把过期时间重新设为 10 分钟，保证每次锁满 10 分钟；登录成功就删掉。所以锁定到期后自动解除，不用改 `SYS_USER` 表，后端重启也不影响。用户名不存在也照样计数，提示语和"密码错误"一样，不让人借此猜出哪些用户名存在。
