## 沟通与文档

- 用通俗易懂的话，讲复杂概念多用类比。文档用短句和常用中文，技术词第一次出现时顺手解释一句；类名、接口路径、命令、协议字段保持原样。
- 回答关于本文件或文档的疑问前，先核对代码、配置或实际运行结果。文档和运行结果不一致时，先确认预期，再改实现或改文档。
- 标"待确认"的地方先问用户，再实现。
- **设计文档在 `docs/`，从 `docs/00-读我.md` 看起**，"待确认"清单也在那里。分工：本文件管规则，`docs/` 管设计细节（表、接口、页面、文件格式）。两者冲突时先问用户，再同步修改。每条规则只在一处写全，其他地方引用。

## 项目

专为**井下**打造的职工健康管理系统：职工佩戴智能手表上传体征，矿上的人员定位系统提供谁在井下、在哪个位置，两边数据合起来在大屏上展示。页面布局和视觉风格要与参考截图（`reference/screenshots/`）几乎一致，细节见 `docs/09`；与截图不同的地方也列在那里。代码、数据库全部重新做，图片素材按相近风格自己绘制。

## 仓库与协作

- 根目录是唯一的 Git 仓库，Git 操作在根目录执行。
- 未经用户明确要求，不提交、不推送、不修改 `origin`。
- `health-v2/.gitignore` 已忽略 `.env.local`、`reference/`、`runtime/`。含密码、矿上地址、真实姓名的文件都不能提交。

- 后端 Java 21 + Spring Boot（Maven）；前端 Vue 3 + TypeScript，`<script setup>`。
- 数据库 Oracle：本机 Docker 容器 `local-oracle-free`，`127.0.0.1:1521`，服务名 `FREEPDB1`，用户 `HEALTH_V2`，连接信息在 `health-v2/.env.local`。密码不写进代码、文档、日志或提交。数据库重新设计，不照搬 SQL Server 脚本；建表脚本显式执行，不在业务请求里自动建表。表设计见 `docs/04`。

## 已定规则

**人员定位数据**（细节见 `docs/02`）

- 数据来源是国家煤监局《煤安监办〔2019〕42号 附件2》协议，厂家经 FTP 传 `.txt`；只用其中井下作业人员部分。
- 后端每 30 秒自动扫描收件箱目录 `runtime/inbox/` 并解析。开发期用户直接把文件放进去；上线后由 FileZilla Server 接收厂家的 FTP 上传并落到这个目录。
- 文件完整性看末尾是不是 `||`；处理完的文件备份保留，不自动删除。只有 `RYCS`、`RYCY`、`RYYJCS` 收到后直接删除（不备份）。
- 数据冲突以文件头里"数据上传时间"最新的为准，不看到达先后。
- 人员唯一标识是人员卡编码（17 位），界面显示"卡号"（后 5 位）。出生年月是厂家占位值，年龄由人工录入。厂家提供的字段（姓名、部门、工种、职务）只读。
- 术语：**基站**是巷道里固定不动、有坐标的定位设备（类比 5G 基站）；**识别卡**是人随身携带的卡。
- 人的位置只精确到"离他最近的基站"。厂家的基站坐标不可用，基站位置由用户在地图上手动摆放，所有有账号的人都能用；摆放操作必须写操作日志（谁、何时、做了什么、前后位置）。基站未摆放的人，地图上不画点，列表里显示区域名称并标"基站未摆放"。

**坐标系**（细节见 `docs/06`）

- 地图统一用 EPSG:4527。CAD 图基准是 2000 还是西安 80 无法从图上判断，待矿上确认（`docs/00` 第 16 项）；目前按图上的原始数字使用。
- 前端请求 GeoServer 用 WMS 1.1.1（EPSG:4527 官方轴顺序是先北后东，与 CAD 数据相反，WMS 1.3.0 会错位）。

**手表**（细节见 `docs/03`）

- 先用模拟器，发到 TCP `9001`；真实手表的接入方式待用户通知。协议参考仓库根目录《智能手表开发协议.docx》。老项目的代码只作参考，需要的复制过来再改。
- Netty 线程里不做数据库写入；用有界线程池，队列满时回压，不创建无限线程。
- 定位模拟器按协议格式生成 `.txt` 放进收件箱，不绕过文件直接写库。

**告警**（细节见 `docs/03`、`docs/05`）

- 告警是"发生过"的记录，只用来展示和统计，没有状态。复制老项目的告警代码时，不带它的处置流程。

## 数据真实性

- 前端只展示后端返回的数据，不自己生成、替换或估算业务数据。数据来源是模拟器可以，前端伪造不行。
- 没有数据显示"暂无数据"或"未录入"，不显示 `0`。
- 手表数值展示采集时间，不用请求时间冒充。
